## Purpose

Establish the foundational substrate — the builtin host core, storage schema, plugin runtime, host-fn ABI, observability, auth, and tenant enforcement — that every subsequent capability-family increment (`0.2.0`–`1.0.0`) rides on, without which no plugin can be loaded, no MCP verb dispatched, and no content stored.

## Requirements

RFC-2119 keywords used throughout. `SHALL`/`MUST` = mandatory. `SHALL NOT`/`MUST NOT` = prohibited. `SHOULD` = preferred. `MAY` = optional.

### R-0001 — Storage layout (anchors [P-0001](../src/adrs/P-0001-storage-layout.md))

- R-0001-a: The system SHALL persist each logical artifact as a single content-substrate row using the C1 single-document layout: `id` (ULID), `workspace_id` (NOT NULL), `type`, `frontmatter` (JSONB), `body` (nullable text), `frontmatter_version`, `migrated_from` (system field), `migrated_at` (system field), `created_at`, `updated_at`.
- R-0001-b: The system SHALL NOT store `migrated_from` or `migrated_at` inside the `frontmatter` JSONB column; these are dedicated system columns. `frontmatter_version` SHALL live authoritatively inside the `frontmatter` JSONB column (the interchange format is self-describing); the dedicated `frontmatter_version` column SHALL be a `GENERATED ALWAYS AS ((frontmatter->>'frontmatter_version')::bigint) STORED` no-drift projection of that JSONB key, so the typed column cannot diverge from the authoritative JSONB value.
- R-0001-c: The system SHALL enforce `CHECK (frontmatter ? 'id')` and `CHECK (frontmatter ? 'frontmatter_version')` constraints at the schema level on all artifact tables.
- R-0001-d: The system SHALL create per-artifact-type tables (not a polymorphic single table) for each plugin-owned content family; per-type expression indexes SHALL be declared at schema initialization for hot query fields (`status`, `priority`, `project_id`, `parent_id`).
- R-0001-e: The system SHALL implement a trigger-based shadow table (`<artifact>_history`) for mutation history on each artifact table, populated on UPDATE; the shadow table SHALL preserve the prior row's frontmatter value byte-for-byte. On `artifact.delete`, the host SHALL write a history row with `operation = 'DELETE'`, `old_frontmatter` = the artifact's pre-deletion frontmatter value, and `old_body` = the artifact's pre-deletion body value, before executing the DELETE; this row is retained under the shadow table's standard retention schedule.
- R-0001-f: The system SHALL maintain materialized projection views over the artifact tables, refreshed via a host-owned queue on host-fn write completion; the V0 refresh mechanism SHALL use `REFRESH MATERIALIZED VIEW CONCURRENTLY` triggered by the host-fn write path; a background worker SHALL drain the refresh queue.
- R-0001-g: The system SHALL enable `pgvector` (bundled with the embedded Postgres engine — `postgresql_embedded` + `pgvector_compiled`, per [P-0010](../src/adrs/P-0010-storage-substrate-engine.md)) in the schema initialization; V0.1+ activation of vector columns (`embedding vector(1536)`) and full-text columns (`search_tsv tsvector`) SHALL be non-breaking `ALTER TABLE ADD COLUMN` additions to the existing tables. *(Amended 2026-06-08 per [P-0010](../src/adrs/P-0010-storage-substrate-engine.md): `timescaledb` is removed from V0 extension installation — D8 demotes TimescaleDB off the V0 stack. Re-derived 2026-06-09 per [observability baseline](../src/architecture/overview.md#observability) (E1 dispositioned = re-derive now): the observability metrics/events surfaces (R-0004) are re-derived to storage-independent emission (stdout/OTel), not in-app hypertables; there is no in-app observability store at V0. See R-0004 and R-0013-c.)* *(Amended 2026-10-19, #4018: the parenthetical "bundled with the embedded Postgres engine — `postgresql_embedded` + `pgvector_compiled`" is superseded. `pgvector` is installed in the operator's instance by the operator and **verified** by the host at a supported version (R-0117-b); the host SHALL NOT run `CREATE EXTENSION` itself. The non-breaking `ALTER TABLE ADD COLUMN` activation path is unchanged.)*

### R-0002 — Core plugin partition (anchors [P-0002](../src/adrs/P-0002-core-plugin-partition.md))

- R-0002-a: The system SHALL designate `tasks`, `repos`, and two further artifact-family plugins (the `0.12.0` and `0.13.0` capability families) as `core: true` plugins, each running as a Wasmtime-hosted WASM Component Model module, signed by the mnemra root, structurally non-uninstallable at runtime.
- R-0002-b: The system SHALL designate workspace, users, agents, authentication, agent sessions, per-plugin permissions, and projects as builtin components compiled into the host process; builtins SHALL NOT execute inside the Wasmtime plugin sandbox.
- R-0002-c: The system SHALL initialize all seven builtins before any plugin is loaded; no plugin invocation SHALL precede builtin startup completion.
- R-0002-d: The system SHALL block runtime uninstallation of any `core: true` plugin; the only path to remove a `core: true` plugin is a binary rebuild.
- R-0002-e: The increment-to-plugin assignment (which of the `0.2.0`–`0.14.0` capability families map to which of the four `core: true` plugins) SHALL be ratified by the maintainer before the `0.2.0` implementation dispatch; the assignment is flagged as a Spec-stage open item in Out of Scope.
- R-0002-f: The content-corpus migration handler (`0.14.0`) SHALL execute as a builtin migration handler, NOT as a `core: true` plugin, because migration is a one-shot destructive control-plane operation gated on the admin token.

### R-0003 — Plugin manifest schema (anchors [P-0003](../src/adrs/P-0003-plugin-manifest.md))

- R-0003-a: Every `core: true` plugin SHALL ship a manifest file at `<plugin-name>/manifest.toml` declaring `schema_version = 1`, `core = true`, `name`, `version`, and the `[verbs]`, `[content_types]`, `[state_scopes]`, `[host_fns]`, and `[signature]` sections as defined in [P-0003](../src/adrs/P-0003-plugin-manifest.md).
- R-0003-b: The runtime SHALL compile a per-instance host-fn allowlist from the signed manifest's `[host_fns]` section before any plugin instance is created; host-fn calls outside the allowlist SHALL fail at the WIT boundary, not at the host-fn body.
- R-0003-c: The runtime SHALL load manifest files using a `schema_version` branch; a V0 plugin presenting `schema_version: 1` to a newer runtime SHALL continue to load; a future manifest presenting an unknown `schema_version` SHALL produce a structured load error.
- R-0003-d: Plugin manifests SHALL NOT include `workspace_id` as a parameter on any write-path host-fn declaration; the host SHALL derive workspace context from the `WorkspaceCtx` bound at request ingress. Note: the [P-0003](../src/adrs/P-0003-plugin-manifest.md) manifest example shows `workspace_id: str` in the inline comment for `projection.emit` — this illustrates the host-fn's internal full signature (including host-derived parameters); it is NOT a plugin-callable parameter. The manifest `[host_fns]` section governs access control (which functions a plugin may call), not the calling convention. The normative calling convention is the API Contract table: `projection.emit(projection_name: str, data: JSON) -> ()`.
- R-0003-e: The runtime SHALL reject at load time any plugin manifest where `core = false`; non-core plugin installation is V0.1+ scope.
- R-0003-f: The runtime SHALL validate plugin output against the WIT-declared schema; size caps per field SHALL be enforced; the parser SHALL fail shut on schema mismatch rather than truncating.
- R-0003-g: The `artifact.delete` host-fn SHALL require explicit declaration in the manifest's `host_fns.required` array; it SHALL NOT be granted by default.

### R-0004 — Observability shape (anchors the [observability baseline](../src/architecture/overview.md#observability); re-altituded out of the [P-0004](../src/adrs/P-0004-observability-shape.md) ADR framing)

*Re-derived 2026-06-09 (E1 disposition: separate observability **generation** from **storage**) and re-altituded out of the project-ADR layer to the [observability baseline](../src/architecture/overview.md#observability) (a theory-trait baseline; observability is a theory trait + chassis mechanism, not a per-project ADR). The server EMITS telemetry storage-independently from the bare shell; it does NOT own where telemetry lands. The original P-0004 framing (TimescaleDB metrics/events hypertables + retention policies + continuous aggregate, all in the app's own Postgres) is removed — it baked observability storage into the substrate; P-0004 is `deprecated` (no successor ADR). The V0 observability storage backend is deferred behind the separation (option set {Prometheus, InfluxDB, TimescaleDB, plain Postgres tables}, named tripwire); the bare shell carries no in-app observability store.*

- R-0004-a: The system SHALL emit a per-verb metric record on every MCP verb dispatch with the V0 emission floor: `workspace_id` (UUID), `verb` (TEXT), `outcome` (TEXT, one of `"ok"`/`"error"`/`"timeout"`), `duration_ms` (INT, wall-clock), `recorded_at` (TIMESTAMPTZ). The emission SHALL be OpenTelemetry (OTel) metric/structured form, exportable to a configurable OTLP endpoint; no artifact IDs, content fragments, or agent identity SHALL appear in the metric record. The metric record SHALL NOT be written to an in-app observability hypertable or table at V0.
- R-0004-b: The system SHALL emit an event record with the V0 emission floor: `workspace_id` (UUID), `event_type` (TEXT), `event_version` (INT, DEFAULT 1), `token_id` (UUID, nullable; derived by host from `WorkspaceCtx`, not plugin-supplied), `agent_id` (UUID, nullable), `session_id` (UUID, nullable), `payload` (JSON; never contains artifact bodies), `recorded_at` (TIMESTAMPTZ). The event SHALL be emitted as a structured/OTel record; it SHALL NOT be written to an in-app observability hypertable at V0.
- R-0004-c: The system SHALL NOT initialize any in-app observability storage at V0 — no metrics/events TimescaleDB hypertable, no observability `add_retention_policy`, and no continuous aggregate. *(Observable: after `mnemra init`, `\d+` lists no metrics/events hypertable and `\dx` does not list `timescaledb`.)* The observability storage backend is deferred behind the generation⊥storage separation (observability baseline, L4 tripwire); telemetry retention at V0 is the operator's stdout/scrape-target retention, not an in-app policy. A persistent observability store is adopted on the named tripwire (when persistent observability storage becomes load-bearing for a real operator deployment).
- R-0004-d: The system SHALL emit structured log records to **stdout** (one structured/JSON line per record), carrying a level, message, timestamp, and `workspace_id` on every tenant-scoped record. Log routing, shipping, and retention are the operator's process-supervisor/log-shipper concern at V0; the system SHALL NOT write logs to an in-app Postgres `logs` table or run an in-app log-retention worker at V0. *(This retires the P-0004 in-app `logs` table + 30-day retention worker — an in-app storage sink the generation⊥storage separation removes.)*
- R-0004-e: *(Retired — re-derived to R-0004-c.)* The P-0004 continuous-aggregate-over-the-metrics-hypertable requirement is removed: there is no in-app metrics hypertable at V0. `p50`/`p95`/`p99` per `(verb, workspace_id, outcome)` remain **derivable** from the emitted `duration_ms` values by the operator's observability backend (R-0004-a guarantees the raw distribution is emitted); the aggregate, if wanted, is computed at the operator-chosen sink, not materialized in the app's substrate.
- R-0004-f: The system SHALL emit a per-verb metric record (per R-0004-a) to the OTel/stdout surface on every MCP verb dispatch, recording `workspace_id`, `verb`, `outcome`, and `duration_ms`. Emission SHALL succeed and the metric SHALL be observable on the emission surface even when no persistent observability backend is configured (storage-independent emission).
- R-0004-g: The system SHALL expose a `GET /health` endpoint as the **first API**, started before config load and before the MCP server begins accepting requests, on a dedicated loopback-only TCP listener. This listener SHALL bind to `127.0.0.1` only (not `0.0.0.0` or `::`) at V0. The listener SHALL NOT be the MCP stdio transport — it is a separate, minimal HTTP server for liveness and readiness probing only, and does NOT constitute an HTTP MCP transport for the purposes of R-0010-e. The listener port SHALL be configurable via `MNEMRA_HEALTH_PORT` env var (default: `8877`). The listener SHALL serve only `GET /health`; it SHALL NOT serve any other HTTP routes at V0. Because the listener binds loopback-only (`127.0.0.1`) at V0, **the loopback bind IS the gate on the detail body** — every caller that can reach the listener is necessarily on loopback, so the `/health` endpoint SHALL return the structured detail body to every caller it can serve: `{ "postgres": bool, "pgvector": bool, "workspace_default": bool, "overall": "ok" | "degraded" | "down" }`. There is no admin-token gating on the detail body at V0. *(Named tripwire: if the `/health` listener ever binds a non-loopback interface, admin-token gating on the detail body becomes required — at that point the detail body SHALL be served only to callers presenting a valid admin token, and unauthenticated callers SHALL receive a status-code-only response.)* The body reports the substrate dependencies the standalone binary owns (the embedded Postgres engine and its bundled `pgvector`); the `timescaledb` field is removed (TimescaleDB is not a V0 substrate dependency per [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) D8). *(Amended 2026-10-19, #4018 — R-0118 splits this one endpoint into three contracts. What carries unchanged: the dedicated loopback-only listener, `MNEMRA_HEALTH_PORT`, "first API, bound before the MCP server accepts", "not an MCP transport", and the non-loopback-bind tripwire. What changes: the listener serves exactly two routes, `GET /health` (liveness: process alive and not wedged, **never** dependent on the instance) and `GET /ready` (readiness: can the host serve, with machine-readable reasons); the `{postgres, pgvector, workspace_default, overall}` detail body is superseded by the R-0118-f readiness body, whose fields are the R-0117 check results. "SHALL serve only `GET /health`" becomes "SHALL serve only `GET /health` and `GET /ready`". The signing-to-runnable spec's R-0022-b (`docs/specs/2026-06-30-signing-to-runnable.md`, "bound first") is unaffected in its ordering clause and inherits the two-route surface. MEASURED at `57cfeca`: today one route serves all three questions — `libs/mnemra-host/health.rs:623-625` answers `503 {"ready": false}` until `ReadinessHandle::mark_ready` (`:200`), then serves `schema::init::health_snapshot` (`libs/mnemra-host/schema/init.rs:757`), which runs `SELECT 1` (`:759`) and reports `overall: "down"` when the instance is unreachable (`:778-785`); an orchestrator liveness probe pointed at it restarts the process on a database outage — the loop R-0118 exists to prevent. Also MEASURED: `health.rs:627-629` returns HTTP `200` for any `Ok` snapshot, including `overall: "down"` and `"degraded"`, which contradicts this requirement's `503` scenario; recorded, not fixed here.)*
- R-0004-h: The system SHALL NOT include artifact bodies, content fragments, or raw query strings in any emitted metric, event, or log record; redaction at the emission (log-write) boundary SHALL be enforced for high-entropy strings.
- R-0004-i: The `event_version` field on every event record SHALL be incremented on breaking event-type schema changes; backward-compatible additions SHALL NOT increment `event_version`.

### R-0005 — Signing chain (anchors [P-0005](../src/adrs/P-0005-v0-signing-chain.md))

- R-0005-a: Plugin signature verification SHALL be synchronous on plugin load; the host SHALL NOT create a plugin instance until `verify()` returns `Ok`; no "verify-async" or "defer to background" path SHALL exist in the load pipeline.
- R-0005-b: If signature verification fails (malformed signature, unknown key, certificate-chain break), the plugin load SHALL be rejected with a structured error naming the plugin; no "best-effort load" path is permitted.
- R-0005-c: The signing key SHALL reside on the build host's filesystem at mode 600, owner = build-pipeline process UID; the signing key SHALL NOT be co-located on the deployment node; the deployment node SHALL receive only signed artifacts and verification material.
- R-0005-d: The verification material (root public key / cert) SHALL be embedded in the mnemra-core binary at build time; no runtime key-fetch path is permitted at V0.
- R-0005-e: The system SHALL fire the multi-deployment trip-wire — requiring `{{P-SigningKeyCustodyHardening}}` (Tier-C ADR, not yet authored) to be authored before any deployment beyond the maintainer's single dogfood instance proceeds.
- R-0005-f: On host startup, the system SHALL check that the admin-token file and signing-verification-material file are both mode 600 and not world-readable; if either check fails, the host SHALL refuse to start.
- R-0005-g: The runtime SHALL reject at V0 any plugin whose manifest does not carry `core: true` signed by the mnemra root; non-core plugin installation is blocked at the load path.
- R-0005-h: The runtime SHALL determine `core` status by signature provenance, NOT by manifest-field trust. A manifest carrying `core = true` SHALL be honored as core ONLY when its signature chains to the mnemra root verification material; a manifest with `core = true` signed by any other key SHALL be rejected at load, regardless of whether non-core plugin installation is enabled (V0) or opened in future stages (V0.1+). The core-vs-non-core determination is structural, bound to the mnemra-team-defined identity of the four core plugins; the binding SHALL NOT be relaxed when V0.1+ non-core plugin installation opens.

### R-0006 — Tenant enforcement (anchors [P-0006](../src/adrs/P-0006-v0-tenant-enforcement.md))

- R-0006-a: Every host-fn signature SHALL take a `WorkspaceCtx` as its first typed parameter; the compiler SHALL enforce this; it SHALL NOT be possible to author a host-fn implementation that issues a database query without receiving a `WorkspaceCtx`.
- R-0006-b: `WorkspaceCtx` SHALL be constructed at a single location in the MCP verb dispatch path, after token validation; there SHALL be no alternative construction path in production code.
- R-0006-c: `workspace_id` extraction from `WorkspaceCtx` SHALL use the `WorkspaceCtx::workspace_id()` accessor only; direct field access SHALL be private; raw `workspace_id` parameters on write-path host-fns are prohibited by ABI. Implementation note: [P-0009](../src/adrs/P-0009-rls-admin-token.md)'s `WorkspaceCtx` struct example shows `pub workspace_id` to illustrate the logical field — this is illustrative of field presence, not its Rust visibility. The normative requirement from R-0006-c takes precedence: the field SHALL be private (`workspace_id: Uuid`), with a public accessor `pub fn workspace_id(&self) -> Uuid`.
- R-0006-d: All read-path host-fns SHALL include `workspace_id = ctx.workspace_id` as a WHERE-clause condition, derived from the `WorkspaceCtx` argument, not as a post-read filter; a CI lint check SHALL assert this on all read paths.
- R-0006-e: Builtin components SHALL use the same `WorkspaceCtx` threading as plugins; there SHALL be no "internal" bypass path that issues a database query without a `WorkspaceCtx` argument.
- R-0006-f: Test harnesses SHALL construct `WorkspaceCtx` via a test-only constructor gated to `#[cfg(test)]`; this constructor SHALL NOT be callable in production code paths.
- R-0006-g: The RLS column-shape (`workspace_id NOT NULL` on every artifact table) SHALL ship at `0.1.0`; RLS policy objects (CREATE POLICY statements) SHALL NOT be activated at V0; they are additive V0.1+ additions per the accepted-risk `R-0001` trip-wire.

### R-0007 — Plugin resource limits (anchors [P-0007](../src/adrs/P-0007-plugin-resource-limits.md))

- R-0007-a: The Wasmtime engine configuration SHALL enable fuel metering via `Store::set_fuel`; the V0 fuel ceiling SHALL be 10,000,000,000 ticks (10B) per verb invocation.
- R-0007-b: The Wasmtime engine configuration SHALL enable epoch-interruption; the V0 epoch deadline SHALL be 5 seconds wall-clock per verb invocation, achieved via `Store::set_epoch_deadline(500)` with a host epoch-tick thread advancing the counter every 10ms.
- R-0007-c: The Wasmtime per-instance memory ceiling SHALL be 64 MiB, enforced via `Config::static_memory_maximum_size` or a `ResourceLimiter`.
- R-0007-d: Table and instance limits SHALL use Wasmtime defaults; plugin instance count SHALL be bounded by the pool size (3–5 per plugin type at V0).
- R-0007-e: When any resource-limit violation fires (fuel exhaustion, epoch deadline, memory ceiling), the system SHALL: (1) catch the Wasmtime trap; (2) emit a structured event with `(workspace_id, plugin_id, plugin_version, limit_type, limit_value)` (destination per R-0004); (3) poison the pool slot and replace it with a new instance; (4) return a structured error to the caller for the current verb invocation.
- R-0007-f: The system SHALL NOT propagate a Wasmtime trap as a host-process panic; kill-and-replace is the recovery invariant.
- R-0007-g: Both fuel AND epoch-interruption SHALL be active simultaneously at V0; disabling either is not permitted.
- R-0007-h: The host epoch-tick thread SHALL be started before any plugin is invoked; the thread SHALL be supervised and SHALL NOT be restarted silently on crash. On epoch-tick thread crash, the host SHALL emit a structured event of type `epoch_tick_thread_died` (destination per R-0004); the host SHALL refuse to accept new plugin invocations until the thread is confirmed restarted; the host SHALL attempt one supervised restart per minute with backoff. The `overall` field of the `/health` response SHALL reflect `"degraded"` while the epoch-tick thread is dead.
- R-0007-i: The Wasmtime version SHALL be pinned in `Cargo.toml` (no wildcard `*` or open `>=` version constraints for the Wasmtime crate); the pinned version SHALL be recorded in the SBOM produced by `verify-build`. An upgrade to a new Wasmtime major or minor version SHALL require explicit approval (per the workspace dependency-approval model); it SHALL NOT be auto-merged by dependabot or equivalent.

### R-0008 — Admin token shape (anchors [P-0008](../src/adrs/P-0008-admin-token-shape.md))

- R-0008-a: The admin token value SHALL be 32 bytes cryptographically random, base64url-encoded (43 characters without padding); no structural content SHALL be encoded in the token bytes.
- R-0008-b: The system SHALL store `BLAKE3(token_bytes)` in `admin_tokens.token_hash`; the raw token bytes SHALL NOT be stored in the database. Token authentication SHALL look the row up by `BLAKE3(presented_token_bytes)` against the unique `token_hash` column. Because the admin token is a 256-bit CSPRNG value (R-0008-a) compared via its BLAKE3 hash, comparison-timing attacks are not applicable and no constant-time comparison primitive is required on this path. (Constant-time comparison remains required where it does apply, e.g. the signing-chain verification path per P-0005.)
- R-0008-c: The `admin_tokens` table SHALL have the schema: `id UUID PK, token_hash BYTEA NOT NULL UNIQUE, workspace_id UUID NOT NULL, scopes TEXT[] NOT NULL, created_at TIMESTAMPTZ NOT NULL, rotated_at TIMESTAMPTZ`.
- R-0008-d: The `workspace_id` column in `admin_tokens` SHALL be NOT NULL; a token row with NULL `workspace_id` is a schema violation; absence of a workspace claim SHALL cause a hard auth failure, not a default to any workspace.

### R-0019 — Plugin invocation / export ABI (anchors [P-0013](../src/adrs/P-0013-plugin-invocation-model.md))

- R-0019-a: The plugin invocation ABI SHALL be typed per-verb exports. - R-0019-d: Domain / non-CRUD verbs (e.g., `echo.audit`) are deferred past V0; their export ABI SHALL be typed too when designed (no string hatch). A manifest-declared verb with no matching typed export SHALL be non-dispatchable at V0 and SHALL return a structured error; this non-dispatchable path SHALL NOT alter the pre-dispatch permission path (the `echo.audit` denial is pre-dispatch and is unaffected — the existing permission tests are not changed by the absence of a typed export).
- R-0019-e: The export ABI SHALL be observable on the contract: a built content plugin component SHALL export the typed `content` interface (`create`/`get`/`list`/`update`/`delete`) and SHALL NOT export a `run`-shaped string-dispatch function; an MCP request for a manifest-declared verb with a corresponding typed export SHALL dispatch to that typed export; an MCP request for a manifest-declared verb with no corresponding typed export SHALL return the R-0019-d structured non-dispatchable error and SHALL leave the pre-dispatch permission outcome unchanged.

### R-0020 — Artifact-list keyset (cursor) pagination behavior (anchors [P-0006](../src/adrs/P-0006-v0-tenant-enforcement.md), [P-0013](../src/adrs/P-0013-plugin-invocation-model.md), the [artifact-list keyset-pagination Frame](../intent/artifact-list-paging-frame.md))

*(Added 2026-06-29 per the [artifact-list keyset-pagination Frame](../intent/artifact-list-paging-frame.md) (Frame-exit gate passed, blob `31515f1`) and its [intake](../intent/artifact-list-paging.md) — a maintainer-locked in-place amendment. R-0020 pins the pagination **behavior** contract both interface directions must satisfy: the import-side `artifact.list` host-fn (R-0012-a/-f) and the export-side `content.list` (R-0019-a); the signature changes themselves are reconciled in the API Contract tables and noted on those requirements. Keystone anchor: `P-LockContract` re-derive-on-reshape — the original `-> list<string>` no-paging contract was locked under a "no unbounded-growth pressure on the list path" assumption that measured append-only growth falsified, so the contract is re-derived against the new world (bounded, resumable, hard-capped pages), not honored as frozen. No new project ADR: keyset-over-offset is recorded as a Non-goal rejection (see Out of Scope), and the amendment is pure application of P-0006 / P-0013 / P-0001 plus the spec R-IDs.)*

- R-0020-a (keyset mechanism — fetch-one-extra): The `artifact.list` read path SHALL paginate by **keyset (cursor)** over the ULID-as-text primary key. It SHALL issue `... WHERE workspace_id = ctx.workspace_id AND type = $type AND <filters> AND id > $cursor ORDER BY id LIMIT $effective_limit + 1`, fetching **one extra row** to derive `has-more` without a `COUNT`. The keyset predicate `id > $cursor` SHALL **AND with** the existing `filters` predicate (R-0012-a) — pagination composes with filtering, it does not replace it — and SHALL retain `workspace_id = ctx.workspace_id` as a WHERE-clause condition (R-0006-d, preserved unchanged). Order is by `id` (ULID-as-text PK; lexicographic = chronological), so pages are returned in stable creation order. When `cursor` is absent (`none`), the read path SHALL omit the `id > $cursor` predicate and return from the first row in `id` order. Concurrent-insert semantics are **forward-non-losing, not snapshot-isolated**: under the spec's `id` ordering (ULID-text PK, lexicographic = chronological — see above), a row created after the cursor's row sorts at `id > $cursor` for any cursor already passed, so it appears on a **later** page of the same walk; an already-emitted row (`id <= $cursor`) is never revisited. The walk therefore neither **loses** already-emitted rows nor **duplicates** them, though it MAY **include** rows created after the walk began — this is the defined keyset behavior (a walk is not a point-in-time snapshot), not a gap. *(Binary-observable on the emitted SQL: it contains `ORDER BY id`, `LIMIT $effective_limit + 1`, the `workspace_id =` condition, and — when `cursor` is `some` — the `id > $cursor` predicate; it issues no `COUNT`.)* [Frame D2]

- R-0020-b (page record + the single invariant): `artifact.list` (and the `content.list` export) SHALL return the WIT record `artifact-page { ids: list<string>, has-more: bool, next-cursor: option<string> }` in place of the prior `list<string>` / `[{ id, frontmatter }]` shape (see the API Contract reconciliation; the record is a WIT component type per R-0012-f). The following invariant is **intrinsic to the page contract and locks at V0**: **`has-more = true` if and only if `next-cursor = some`.** When `has-more = true`, `next-cursor` SHALL be the `id` of the **last row** in the returned page (the value a caller passes as `cursor` to resume — `id > next-cursor`); when `has-more = false`, `next-cursor` SHALL be `none` and the returned `ids` SHALL NOT include a `cap+1`-th row. The return is **ids-only**: it carries no inline frontmatter. This is the shape locked by **intake Success criterion 1** (the host-fn `artifact-list` return record `{ ids: list<string>, has-more, next-cursor }`) and **Success criterion 2** (the symmetric guest export) — not a documentation fix. *(Anchor correction: the upstream lock for the ids-only narrowing is **intake SC1/SC2**, not Frame D4. Frame D4 understated the import baseline, modeling the prior return as `list<string>` for both directions, whereas the host-fn import baseline was `[{ id, frontmatter }]` with frontmatter inline; the import side therefore genuinely **drops inline frontmatter**, a narrowing D4 did not address.)*

  **Accepted V0 characteristic — the ids-only return shifts frontmatter hydration to the caller (N+1):** because the page carries no inline frontmatter, a caller wanting frontmatter for a page resolves it via `artifact.get` per id — up to `effective_limit` `artifact.get` calls for a full page (an N+1 fan-out; `artifact.get` returns frontmatter **and** body, and no frontmatter-only get exists at V0, so each call also over-fetches the body). This is the accepted V0 trade-off (consistent with the data-minimization posture also reflected in R-0012-b); the ids-only shape is **provisionally accepted** by the maintainer 2026-06-29, with the revisit gated on dogfood evidence — see the ids-only-return tripwire in Out of Scope. **V0 dogfood instrumentation SHALL capture** (a) the per-`list` `artifact.get` fan-out count and its latency distribution, and (b) the access-pattern signal — **filter-then-fetch** (a targeted `list` whose handful of ids are individually fetched) versus **list-then-N+1-get-for-metadata** (a `list` followed by a full-page `artifact.get` fan-out purely to read frontmatter) — so reality can (i) validate that the fan-out keeps pool pressure within the fixed 3–5-slot budget (R-0016-a) and (ii) feed the ids-only-vs-frontmatter revisit. *(Binary-observable on every response: the `has-more ⇔ next-cursor = some` biconditional holds, including the last-page case `has-more = false ∧ next-cursor = none`; `next-cursor` equals `ids.last()` whenever `some`; and the page carries no inline frontmatter field.)* [intake SC1/SC2 — record shape + ids-only narrowing; Frame D4 — page-record decision (import baseline understated, corrected here); Frame D2 — keyset mechanics]

- R-0020-c (page-size clamp — host-side; the result-set-size DoS bound): The effective page size SHALL default to **exactly 100** and SHALL be hard-capped at **exactly 500**: `effective_limit = (limit == 0 ? 100 : min(limit, 500))` (the `limit = 0` resolution is R-0020-f). The clamp SHALL be enforced **host-side in the `artifact.list` host-fn** — the SQL `LIMIT` owner and the **sole DB chokepoint**: guests are IO-free under the Wasmtime component-model sandbox (R-0002-a/-b), and a guest reaches the DB only through the host-fn ABI (R-0012-a) — and only through the host-fns on its signed per-instance allowlist (R-0003-b), enforced at the WIT boundary — so the host-fn is the necessary-and-sufficient clamp site, independent of any guest-supplied `limit`; a guest-side clamp is optional defense-in-depth only, never the enforcing layer. **No list path SHALL issue an unbounded (`LIMIT`-less) query.** This is the **result-set-size** DoS bound — it closes the *size* half of the prior unbounded-`SELECT` finding; it does **not** bound query **scan cost** (a `LIMIT` bounds rows *returned*, never rows *scanned* — see R-0020-d). *(Binary-observable: a request with `limit = 100_000` against a type holding > 500 artifacts returns `ids.len() <= 500` (clamp) and rows returned `<= cap + 1` (fetch-one-extra); a test asserts no read path emits a `LIMIT`-less query.)* [Frame D5; intake Success criteria 4 + 6; `P-SecurityLayered` — Security default-on, not opt-in]

- R-0020-d (scan-cost backstop — host-side `statement_timeout`, inside an explicit transaction): Because a `LIMIT` does not bound scan cost, a `filters` predicate on a **non-indexed** frontmatter field (outside the four R-0001-d expression-indexed fields `status` / `priority` / `project_id` / `parent_id`) matching sparsely or zero rows forces the keyset `ORDER BY id LIMIT cap+1` to walk the entire `id`-btree tail. The host read-path SHALL therefore open an **explicit Postgres transaction** (`BEGIN`) enclosing **both** a session **`SET LOCAL statement_timeout`** and the keyset query, so a query that would scan unbounded is **canceled** within a bounded wall-clock budget. The explicit transaction is **mandatory**: a `SET LOCAL` issued outside an explicit transaction binds only to the implicit single-statement transaction that commits immediately, so it is a **no-op** for the following query — a `SET LOCAL` outside an explicit transaction SHALL NOT be accepted as compliance (the backstop would otherwise ship **silently disarmed** while every cap test still passes). This backstop is **additive** to the R-0020-c cap — each runtime sub-layer is independently load-bearing (cap = result-set-size bound; timeout = scan-cost bound). On cancellation the dispatch SHALL surface **both**: (1) the **R-0004-a metric `outcome = "timeout"`** (not `"ok"`) with a bounded `duration_ms`; and (2) a distinguishable caller-facing JSON-RPC error code **`query_scan_timeout`** — **distinct from** `plugin_execution_timeout` (the R-0007-b guest epoch-deadline timeout, a guest-*execution* timeout) and **distinct from** `-32602` parameter-invalid (R-0010-f / R-0020-e, an input fault); error classes SHALL NOT be conflated (R-0010-f). The `query_scan_timeout` error body SHALL carry **no Postgres/schema/DB internals** (the same no-leak posture locked in R-0020-e, applied to a **distinct** error class). The shared `outcome = "timeout"` metric value with the epoch timeout is acceptable because the caller-facing error code is the discriminator; the metric stays shared. The Wasmtime epoch deadline (R-0007-b, 5 s) bounds *guest wasm execution*, **not** this host Postgres query (the host-fn query runs while the guest is blocked in the host call, where the epoch deadline cannot interrupt it) — the `statement_timeout` is the only bound on the host query and SHALL be set strictly below the R-0007-b 5 s guest deadline. **Locked value: `statement_timeout = 3000 ms`** (maintainer-ratified 2026-06-29). Rationale: a backstop *ceiling*, not a target; a healthy keyset page read of `<= cap+1` rows over the PK btree completes in single-digit ms (~100× headroom), so 3000 ms never false-trips a legitimate read; defensible band 1000–5000 ms, strictly below the R-0007-b 5 s guest deadline. *(Binary-observable, two independently-assertable parts: **(i) GUC placement** — the emitted `SET LOCAL statement_timeout` value is non-zero and strictly below the R-0007-b 5 s guest epoch deadline, directly assertable from the emitted value and read back as a non-zero `current_setting('statement_timeout')` inside the same explicit transaction; **(ii) cancellation fires** — a query exceeding the timeout is canceled and surfaces both `outcome = "timeout"` and the `query_scan_timeout` caller error. Because a `<= cap+1`-row PK-btree tail scan completes sub-millisecond and cannot reach the locked 3000 ms, part (ii) SHALL be validated with a **test-only reduced `statement_timeout`** — set deliberately low and seed enough rows to exceed it — NOT the production 3000 ms; the production value is exercised only for part (i) placement. The GUC touches no schema, index, filter semantics, or RLS.)* [Frame D8; `P-SecurityLayered` — the deterministic runtime **backstop** sub-layer]

- R-0020-e (cursor validation at the boundary + error semantics): The `cursor` SHALL be validated as a **well-formed 26-char ULID at the `artifact.list` host-fn boundary, before query construction** — this both fixes the error semantics and **caps the otherwise-unbounded `option<string>` input** (an arbitrary-length client string never reaches query construction). On a **malformed** cursor the host-fn SHALL return the **R-0010-f** structured **"parameter invalid"** error — **not** a silently-empty page, **not** a raw Postgres error echoed to the caller — and the error body SHALL carry **no Postgres/schema/DB internals** (an additive no-leak posture locked here; this is not literal R-0010-f text). A **valid-but-out-of-range** cursor (well-formed ULID past the end) SHALL return an **empty page** (`ids = []`, `has-more = false`, `next-cursor = none`), mechanically derivable from keyset `id > $cursor`. A **foreign-but-valid** ULID is safe: confined to the caller's workspace by `workspace_id = ctx.workspace_id` (R-0006-d), it can at most return an empty or shifted page within the caller's own workspace — never another tenant's rows. Layer note: the *validation* runs at the host-fn boundary (the R-0020-c clamp-site layer); the *JSON-RPC error code* is returned by the MCP handler up-stack (the R-0010-f layer) — linked but distinct layers. *(Binary-observable: malformed cursor → R-0010-f "parameter invalid" with no DB/schema string in the error body; out-of-range valid ULID → empty page; a cross-workspace probe under a foreign cursor returns zero foreign rows.)* [Frame D9; error class R-0010-f]

- R-0020-f (`limit = 0` ≠ unlimited): `limit = 0` SHALL resolve to **clamp-up to the default** (effective limit = 100) — every call returns progress. Independent of that resolution, `0` SHALL **never** disable the `LIMIT`: the read path SHALL NOT emit `LIMIT NULLIF($n, 0)`, a `LIMIT`-less query, or any construction where `0` yields an unbounded result set. **Locked value: clamp-up-to-default** (maintainer-ratified 2026-06-29). Rationale: the recorded Frame lean ("every call returns progress"); least-surprising for a caller passing `0` — a normal default page rather than a silently-empty page that reads as end-of-data; the no-unbounded invariant holds under either resolution. *(Binary-observable against the emitted SQL: `limit = 0` emits `LIMIT 101` (default 100 + 1) and returns `ids.len() <= 100`; it never emits `LIMIT NULL` / `LIMIT NULLIF`-zeroed / a `LIMIT`-less query. The non-monotonicity is intentional and not a bug: `limit = 0` → default 100, `limit = 1` → 1 — `0` is the "unspecified, give me a default page" sentinel, not "fewer than one row".)* [Frame D10; intake Success criterion 6; `P-SecurityLayered`]

- R-0020-g (paging params excluded from telemetry): `cursor` (in) and `next-cursor` (out) **are artifact IDs**; R-0004-a forbids artifact IDs in the per-verb metric record. The paging parameters SHALL be **excluded** from the per-verb metric record **and** from structured-log emission: the dispatch's metric/log carries the R-0004-a floor (`workspace_id` / `verb` / `outcome` / `duration_ms`) but never the `cursor` / `next-cursor` values. *(Binary-observable: the emitted per-verb metric record and the structured-log line for a paginated dispatch contain neither the `cursor` nor the `next-cursor` value.)* [Frame D11; R-0004-a, extended to the structured-log surface by the same data-minimization rationale]

*R-0001-a's "persist" means stored as a row — a storage shape. R-0116 is the separate contract that a stored row survives the host stopping and starting again. It applies the maintainer's rulings of 2026-09-15: durability is defined as surviving a stop and restart including a hard kill; data lives outside the executable and its image at an operator-configured location; an operator-provisioned external Postgres server is a future engine, not V0 ("it just moves the problem to the postgres server" — consistent with P-0010's "the V0 engine SHALL be embedded Postgres"); and no requirement says "local filesystem" — the location is the operator's, local or network-backed. Keystone anchors: **V-Reliability** — correctness under failure (a process crash) is designed and measured, never assumed; **P-GuaranteeByMechanism** — each guarantee below is carried by a check that fails loudly, never by an operator convention. The engine change that satisfies these requirements is implementation; the embedded-Postgres crate's default start and connection path does not satisfy them as shipped (R-0116-d, R-0116-e name the specific gaps), and the plan owns the mechanism inside the fences stated there.*

- R-0116-a (the durability invariant): Every write acknowledged to a caller — an `artifact.create` / `artifact.update` / `artifact.delete` host-fn, or the MCP verb wrapping it, that returned success — before the host stops SHALL be reflected identically after the host next starts against the same data directory, for each of three stop shapes: a clean stop (SIGTERM, graceful drain), a hard kill of the host process (SIGKILL), and a hard kill of the embedded postmaster (SIGKILL). "Reflected identically" is defined as: for each acknowledged create/update, `artifact.get` returns a `frontmatter` that is **semantically equal** to the pre-stop read (equal as parsed JSON values — JSONB does not preserve key order, so byte comparison of the serialized form is not the test) and a `body` that is **byte-equal**; each acknowledged delete stays absent; and the per-table row count under the workspace equals the pre-stop count. A write that was **not** acknowledged (in flight at the kill) MAY be present or absent — the invariant binds acknowledged writes only. A write that cannot be durably committed (disk full, `fsync` failure) SHALL NOT be acknowledged: the host SHALL NOT change Postgres's `data_sync_retry` from its default `off` (an `fsync` failure panics the postmaster rather than retrying against possibly-lost pages), and the dispatch surfaces the failure as R-0004-a `outcome = "error"`. *(Binary-observable: the three restart scenarios below, each comparing a pre-stop read set to a post-start read set under the equality rule above; `SHOW data_sync_retry` returns `off`.)* [brief Success criteria "Durable across restart"; V-Reliability]

- R-0116-b (data directory — resolution, integrity checks, and observability): The host SHALL resolve exactly one data directory at startup, before binding any listener, by this precedence: (1) the `MNEMRA_DATA_DIR` environment variable when set and non-empty — it SHALL be an **absolute** path, honored wherever it points (a network-backed mount is the operator's choice); a relative value SHALL be refused with `data_dir_rejected { reason: "relative", guidance }`; (2) otherwise the platform per-user application-data default: Linux `$XDG_DATA_HOME/mnemra` (falling back to `$HOME/.local/share/mnemra` when `XDG_DATA_HOME` is unset), macOS `$HOME/Library/Application Support/mnemra`. No Windows default is defined: the engine's pinned platform set is Unix-only, and R-0116-e's peer authentication is a Unix mechanism. The default SHALL NOT be under the OS temporary directory and SHALL NOT be the executable's own directory or a descendant of it. On **every** start the host SHALL `lstat` the data directory and each of `<data_dir>/pg`, `<data_dir>/host.lock` and the socket directory (R-0116-e) that exists, and SHALL refuse with `data_dir_rejected { reason, guidance }` if any is a symbolic link, is not owned by the host uid, or (for the directories) is group- or world-accessible — `guidance` names the path and the one-line fix (`chmod 0700`, `chown` to the host uid, or replace the symlink); if the resolved directory cannot be created or is not writable by the host uid, the host SHALL refuse with `data_dir_unwritable`. Before any postmaster start the host SHALL emit one structured log record (R-0004-d) of type `data_dir_resolved` carrying `path` (absolute), `source` (`"env"` | `"default"`), `initialized` (`"first_run"` | `"existing"`, per R-0116-c) and `socket_dir` (absolute, per R-0116-e). *(Binary-observable: with `MNEMRA_DATA_DIR` unset and `XDG_DATA_HOME` unset on Linux, the record's `path` is `$HOME/.local/share/mnemra` and `source` is `"default"`; with `MNEMRA_DATA_DIR=/x`, `path` is `/x` and `source` is `"env"`; `MNEMRA_DATA_DIR=relative/x` yields `data_dir_rejected` and a non-zero exit; a read-only `/x` yields `data_dir_unwritable`; a symlinked `/x` yields `data_dir_rejected { reason: "symlink" }`. The resolver takes the platform, environment and home directory as injected inputs so the macOS default is unit-testable on a Linux runner.)* [brief Hard constraints "Data lives outside the executable and its image"; V-Consistency — the same env-override shape as `MNEMRA_TOKEN_FILE` (R-0008-e) and `MNEMRA_HEALTH_PORT` (R-0004-g); P-TestableByDesign — the resolver's inputs are injected]

- R-0116-c (layout, first run, completion marker, no re-initialization): The layout under the data directory is fixed: `<data_dir>/pg` (the embedded cluster's `PGDATA`, mode `0700`), `<data_dir>/host.lock` (R-0116-g), `<data_dir>/initialized` (the completion marker), and — where it fits — `<data_dir>/sock` (R-0116-e). The host SHALL key first run on the **marker**, not on `PG_VERSION`: (i) marker absent and `<data_dir>/pg` absent → first run — the host creates `<data_dir>` and `<data_dir>/pg`, runs `initdb`, writes the cluster configuration (R-0116-d/-e), starts the postmaster, runs the first-run schema bootstrap of R-0013-a, and **only after every preceding step has succeeded** writes `<data_dir>/initialized` and `fsync`s it and its directory; (ii) marker absent and `<data_dir>/pg` present → an interrupted first run — the host SHALL refuse with `data_dir_incomplete_init { data_dir }`, SHALL NOT run `initdb`, and SHALL NOT delete or overwrite anything; recovery is the operator removing the data directory (stated in the error's `guidance` field); (iii) marker present → existing store — the host SHALL NOT run `initdb`, SHALL NOT delete, move, truncate or recreate any file under `<data_dir>/pg`, and SHALL start the postmaster against the existing cluster. The production start path SHALL NOT configure the engine's temporary-directory mode and SHALL NOT remove the data directory on stop or drop; the test fixture's temporary engine (CI tier-2 spec R-0026/R-0027) is a separate construction path and is unaffected. *(Binary-observable: across two consecutive starts against one directory `SELECT system_identifier FROM pg_control_system()` returns the same value (a re-`initdb` mints a new one); a directory holding `pg/` but no `initialized` yields `data_dir_incomplete_init` and the directory's bytes are unchanged; the marker's mtime is later than every file `initdb` wrote.)* [brief Hard constraints; P-GuaranteeByMechanism — first-run identity is a marker written last, not a file `initdb` writes first]

- R-0116-d (durable-commit settings are effective, and checked by the host itself): On the production cluster the effective values of `fsync`, `synchronous_commit` and `full_page_writes` SHALL be `on`, and `data_sync_retry` SHALL be `off`, **as observed on the host's own bootstrap session** at every start: the host SHALL run `SHOW` for each after connecting and SHALL refuse to serve with `data_dir_durability_off { setting, value }` if any differs. The host SHALL NOT weaken them through the engine crate's configuration map, `postgresql.conf`, `ALTER SYSTEM`, per-session `SET`, or **postmaster command-line options**. The last is the load-bearing case: the embedded-Postgres crate's `start()` passes `-F` to the postmaster (`postgresql_embedded` 0.20.4, `src/postgresql.rs:320`, `options.push(format!("-F -p {}", port))`), and `-F` is `fsync = off` at command-line precedence, above `postgresql.conf` and `ALTER SYSTEM`. The production path therefore SHALL NOT start the postmaster through a path that passes `-F`. How that is achieved is plan-tier within this fence — invoking `pg_ctl start` through the crate's own command builders with the host's option string is the path that adds no dependency; an upstream change to the crate is the durable path; **a fork of the crate is a new-dependency posture and is raised to the maintainer, never taken mid-implementation** (P-RaiseDontImprovise). The host's own `SHOW` check is what makes any regression of this fence fail loudly. *(Binary-observable: `SHOW fsync`, `SHOW synchronous_commit`, `SHOW full_page_writes` return `on` and `SHOW data_sync_retry` returns `off` on the host's bootstrap session — asserted by the host at startup — and on the harness's own socket session; the running postmaster's argv contains no `-F`; a start forced to pass `-F` yields `data_dir_durability_off { setting: "fsync", value: "off" }`, the host serves no MCP verb, and the R-0004-g `/health` listener — which binds first by design — reports `overall: "down"`. The forcing seam is the existing `test-hooks` cargo feature's failure injection (`InjectedFailure`, `RunConfig::inject_failure`), which is compiled only into test builds; no always-compiled hook exists for it.)* [V-Reliability; P-GuaranteeByMechanism — the host checks the effective value rather than trusting a configuration it wrote; P-RaiseDontImprovise on the fork option]

- R-0116-e (cluster access: peer-authenticated over a private unix socket, no stored secret, no network listener): The host SHALL reach the embedded cluster **only** over a unix-domain socket in a directory it owns with mode `0700`, authenticated by **peer** authentication; there SHALL be no password-authenticated path and no TCP listener. Concretely: the cluster's `listen_addresses` SHALL be the empty string; `unix_socket_directories` SHALL be the socket directory; `pg_hba.conf` SHALL contain only `local` lines whose method is `peer` with an ident map, and no `host`, `hostssl` or `hostnossl` line; the ident map (`pg_ident.conf`) SHALL map the host's OS user to exactly the roles the host connects as — the bootstrap superuser, the four R-0013-e roles (host-fns, migration, backup, health-probe) and, once provisioned, the [P-0020](../src/adrs/P-0020-report-execution-context.md) report role — and no other OS user to any role. No role SHALL carry a password, and no password SHALL exist at any point: `initdb` SHALL be invoked with `--auth-local=peer --auth-host=reject` and **without** `--pwfile` or `--pwprompt` (initdb 16 accepts this and creates the superuser with no password), and every `CREATE ROLE` the host issues SHALL omit `PASSWORD`. The embedded-Postgres crate's `initialize()` passes `--pwfile` (`postgresql_embedded` 0.20.4, `src/postgresql.rs:268`), so — exactly as R-0116-d fences `-F` — the production path SHALL NOT run `initdb` through a path that passes `--pwfile`. The socket directory SHALL be `<data_dir>/sock` when the resulting socket path fits the platform's `sun_path` limit (104 bytes on macOS, 108 on Linux); otherwise a directory the host creates with `mkdtemp` (mode `0700`) under `$XDG_RUNTIME_DIR` on Linux or `$TMPDIR` on macOS (falling back to the OS temporary directory when the variable is unset) — never a predictable name another user could pre-create — with the choice reported in `data_dir_resolved.socket_dir`; on every connection over the socket the host SHALL verify the peer's uid is its own (`SO_PEERCRED` / `LOCAL_PEERCRED`) and refuse otherwise. There is no `<data_dir>/secrets/`, nothing to rotate, and no credential for a copy of the data directory to carry. *(Binary-observable: `SHOW listen_addresses` returns an empty string; `pg_hba.conf` matches `^local\b.*\bpeer\b` on every non-comment line and contains no line beginning `host`; `pg_ident.conf` parses to exactly one map whose lines map the host's OS user to each role the host connects as, and no line names another OS user; `SELECT count(*) FROM pg_authid WHERE rolpassword IS NOT NULL` returns `0`; the `initdb` argument vector, as logged at debug level by the host's existing engine-setup trace, contains `--auth-local=peer` and `--auth-host=reject` and neither `--pwfile` nor `--pwprompt`; the fallback socket directory, when used, has mode `0700`, is owned by the host uid, and its name is not derivable from the data-directory path.)* *Rejected alternative, kept for the record: password authentication over loopback TCP with the bootstrap and application-role passwords generated once and persisted under `<data_dir>/secrets/` (mode `0700`/`0600`, R-0005-f check extended). Rejected because the secret at rest travels with every copy of the data directory; the crate writes the `initdb` password to the OS temporary directory, `initdb` refuses a non-empty `PGDATA` so the file cannot be hidden under `pg/` either, and a failed `CREATE ROLE … PASSWORD` echoes the literal into the cluster's start log; rotation becomes a standing question with no firing event; and it adds two refusal paths (`credentials_missing`, mode check) that peer authentication does not need. Also rejected: `trust` on the socket — `peer` is strictly stronger at the same cost.* [V-Security — default-on; P-LeastAuthority — each role is reachable only by the one OS user that runs the host; V-DataMinimization — a credential that need not exist is not held; V-Simplicity — dissolves the secrets directory, the backup-carries-a-secret exposure and rotation in one move]

- R-0116-f (engine major-version guard, with the way out stated): On a start where the marker is present (R-0116-c), the host SHALL read `<data_dir>/pg/PG_VERSION` **before any postmaster start attempt** and compare its major version to the major of the engine's pinned version (`EMBEDDED_PG_VERSION` in `libs/mnemra-host/storage/postgres/engine.rs`). On a mismatch — including an unreadable or unparsable `PG_VERSION` — the host SHALL refuse with `data_dir_version_mismatch { data_dir, found, engine_major, guidance }`, SHALL NOT modify anything under `<data_dir>`, and SHALL NOT initialize a second cluster anywhere. `found` SHALL be the parsed major as an integer when the file parses, else `null` — never the raw file content. `guidance` SHALL state the operator's way out in one sentence: run the previous binary whose engine major equals `found`, or migrate the store with the major-upgrade procedure once one exists (Out of Scope). The refusal SHALL be the host's own error, not a Postgres start failure surfaced after the fact. So an operator can learn a binary's engine major **before** pointing it at a store, `mnemra --version` SHALL print `engine_major` alongside the host version. *(Binary-observable: a store whose `PG_VERSION` reads `15` yields `data_dir_version_mismatch { found: 15, engine_major: 16, guidance: … }` and a non-zero exit with no postmaster ever started against `<data_dir>/pg`, and a byte-for-byte comparison of `<data_dir>` before and after shows no change; a `PG_VERSION` containing `garbage` yields the same error with `found: null`; `mnemra --version` output contains `engine_major: 16`; a `PG_VERSION` of `16` proceeds to postmaster start.)* [P-GuaranteeByMechanism — an engine bump against an old store fails loudly at the last cheap point; V-Reliability; P-Defer — the upgrade tooling is deferred and this guard is its self-announcing tripwire]

- R-0116-g (exclusive ownership across restarts, machines and reboots — and what "a live postmaster" means): Ownership of a data directory is carried by `<data_dir>/host.lock`, which the host SHALL create once and SHALL **never unlink or truncate** (an operator deleting it after a confirmed failover is the one manual step, stated in the deployment documentation). **Accepted residual (maintainer ruling 2026-09-17, following the data-location ruling that network-backed directories stay allowed):** recovery after a failover on a network-backed directory depends on the operator confirming that the previous host is stopped; a wrong confirmation during a network partition permits two writers against one cluster. The host cannot test a foreign holder's liveness, so no mechanism closes this; the only alternative — prohibiting network-backed data directories — was declined. This is a recorded residual of that ruling, not an open question. On start the host SHALL open it and take an exclusive non-blocking advisory lock (`flock(LOCK_EX | LOCK_NB)`); on failure it SHALL refuse with `data_dir_in_use { data_dir, holder }`. With the lock held it SHALL read the holder record the previous owner wrote — `{ hostname, boot_id, pid, pid_start_time, engine_major }`, where `boot_id` is the machine-boot identifier (Linux `/proc/sys/kernel/random/boot_id`; macOS `kern.boottime`) — and classify the previous holder: **empty or unparsable record** → refuse with `data_dir_in_use { holder: null }` (the file exists, so an owner wrote it; an unreadable claim is not a dead one); **foreign** (hostname differs **and** `boot_id` differs) → refuse with `data_dir_in_use` **without any liveness test** — a foreign holder cannot be tested from here, and a network-mounted directory is exactly where one appears; **earlier boot** (`boot_id` differs, hostname equal) → reclaim **only if** the data directory is on a local filesystem, determined from the mount's filesystem type (`/proc/self/mountinfo` on Linux, `statfs` on macOS; any network filesystem type, and an undeterminable type, count as not local) — otherwise refuse with `data_dir_in_use`, because machines sharing a network mount routinely share a hostname (a compose `hostname:`, a rescheduled StatefulSet pod) and a reclaim there would start a second postmaster against a live cluster; **same boot** → the recorded pid is live only if a process with that pid exists, is owned by the host uid, has `pid_start_time` within 5 s of its actual start time, and has the host binary in its argv — live → refuse `data_dir_in_use` (the lock should have failed; the record wins); otherwise reclaim. On reclaim the host SHALL rewrite the record with its own identity and `fsync` it before starting the postmaster. The host SHALL then reconcile `<data_dir>/pg/postmaster.pid` under this definition of **a live postmaster**: a process whose pid equals the pidfile's line 1, is owned by the host uid, has `-D <data_dir>/pg` in its argv, and whose actual start time is within 5 s of the pidfile's recorded start epoch (line 3). If the previous holder was from an earlier boot, no such process can exist and the host proceeds without signalling anything. If one exists on the same boot (a postmaster orphaned by a hard-killed host — `pg_ctl` daemonizes it, so it outlives the host; the postmaster-ownership-marker intake, locked 2026-07-07), the host SHALL stop it with a fast shutdown (`pg_ctl stop -m fast`, WAL-safe) and only then start its own. If a process with that pid exists but fails any part of the definition, the host SHALL NOT signal it and SHALL refuse with `data_dir_postmaster_ambiguous { data_dir, pid, guidance }` (guidance: confirm no postmaster runs against the directory, then remove `pg/postmaster.pid`). The host SHALL NOT attach to a postmaster it did not start in the current run. *(Binary-observable: a second host on a directory a live host holds exits with `data_dir_in_use` while the first host's writes continue to read back; a record naming a different hostname and `boot_id` yields `data_dir_in_use` with no signal sent to any process; an empty `host.lock` yields `data_dir_in_use { holder: null }`; a same-hostname earlier-boot record on a directory whose mount type is `nfs4` yields `data_dir_in_use`, while the same record on a local filesystem reclaims; after `kill -9` of a host, the orphaned postmaster is live under the definition, the next start succeeds, and afterwards exactly one `postgres` runs with `-D <data_dir>/pg` in its argv; a `sleep` process holding the pidfile's pid on the same boot yields `data_dir_postmaster_ambiguous` and the `sleep` is still running afterwards; a record from an earlier boot with a pid currently held by any process proceeds without signalling it.)* *Rejected alternative: a bare `flock` as the only ownership mechanism — an unlinked lock file or local-only lock semantics on a network mount would let a second host stop a live postmaster or run beside it.* [V-Reliability; P-GuaranteeByMechanism — ownership is a record plus a lock, not "don't run two"; V-Security — a destructive stop is gated on a full identity match, never on a pid alone]

- R-0116-h (restart acceptance placement — the R-0032 guard-lint fit — and how the harness observes the cluster): The restart acceptance SHALL be **out-of-process**: it spawns the production `mnemra` binary with `MNEMRA_DATA_DIR` set to a per-run directory **under the recipe's per-run `$TMPDIR`** (so an orphan the scenario leaves behind on a failed run is inside `scripts/ci-reap.sh`'s temp-root kill-set), writes through the MCP stdio surface, stops the child by the scenario's method, spawns the binary again against the same `MNEMRA_DATA_DIR`, and reads back over MCP. It SHALL live in the existing `smoke_e2e` gate (`verify-smoke`, `libs/mnemra-host/tests/smoke_e2e.rs` — the out-of-process full-binary cell of the CI tier-2 spec's R-0033 partition) and SHALL NOT live in `startup_run_full` or any fixture-consuming member binary; it therefore constructs no engine in code and needs **no** R-0032 exception — that list stays exactly `{startup_run_full}` and the R-0033 partition is unchanged. The harness discovers what it needs from the child's own output: it parses `data_dir_resolved` from the child's stdout for `socket_dir`, and — running as the same OS user — connects over that socket as the superuser role by peer authentication for the SQL observables (`system_identifier`, the `SHOW` values, `pg_authid`); it reads `<data_dir>/pg/postmaster.pid` for the postmaster's pid. The added CI cost is bounded: at most four child starts per scenario, one gate. *Rejected: an in-process double `run_with` inside `startup_run_full` — a second boot inside one surviving test process does not restart the host (a key-parity failure), and `run_with` returns before serving, so no write path is reachable there; and a new fixture-consuming binary with an added R-0032 exception — it widens a single-sourced list for a test that needs no engine construction.* *(Binary-observable: the restart scenarios pass under `just verify-smoke`; `grep -n 'EmbeddedEngine::start\|start_embedded\|postgresql_embedded' libs/mnemra-host/tests/smoke_e2e.rs` returns nothing; the R-0032 guard lint and the R-0033 reconciliation check stay green with their lists unedited; the per-run data directory's path has the recipe's `$TMPDIR` as a prefix.)* [P-TestableByDesign; P-CheckCoversTheClaim — the check restarts the process the claim is about; CI tier-2 spec R-0032/R-0033]

- R-0116-i (mount requirement — the host-side half of the container posture): When the `MNEMRA_DATA_DIR_REQUIRE_MOUNT` environment variable is set, the host SHALL verify at startup that the resolved data directory is a mount point and SHALL refuse with `data_dir_not_mounted { data_dir, reason, guidance }` otherwise. The check fails closed: a value other than exactly `1` refuses with `reason: "bad_value"`; a platform or environment where the mount table cannot be read (no `/proc/self/mountinfo`, as on macOS) refuses with `reason: "undeterminable"`; only a readable mount table with an entry whose mount point equals the path passes. This is what catches a container started without a volume at the path the operator intended, where data would otherwise land silently in the writable layer. The image-side contract that would set this variable (the image environment, a non-root `USER`, the directory's ownership) is **parked** — see Out of Scope — because no image exists to test it against. *(Binary-observable: with `MNEMRA_DATA_DIR_REQUIRE_MOUNT=1` and `MNEMRA_DATA_DIR` pointing at a plain directory the host exits with `data_dir_not_mounted { reason: "not_mounted" }`; with the same directory bind-mounted it starts; with the variable set to `true` it exits with `reason: "bad_value"`; on a platform without a readable mount table it exits with `reason: "undeterminable"`.)* [brief Hard constraints — the maintainer's verbatim ruling; P-GuaranteeByMechanism — a mount that never landed is refused, not discovered at the first restart; P-SecurityLayered — a control that cannot decide denies]

- R-0116-j (replacement survival — bare binary): The R-0116-a invariant SHALL also hold when, between the stop and the next start, the executable is replaced — the minimal form is the same binary run from a different filesystem path — so that "at the operator's location" is distinguished from "beside the executable" for the bare-binary deployment shape. The container form (a container removed and recreated from a different image with the same volume) is parked with the image contract in Out of Scope until an image exists to run it against. *(Binary-observable: the replace-the-executable scenario below.)* [brief Hard constraints "Data lives outside the executable and its image"; maintainer ruling 2026-09-17 — locked in the bare-binary form; V-Reliability]

### R-0117 — Requirements the host places on the operator-run PostgreSQL instance, each verified by the host, failing closed (Amended 2026-10-19, #4018; anchors [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) §Amendment 2026-10-19, the brief's Success criterion "Durable across restart", the [overview](../src/architecture/overview.md) Reliability / durability axis; maintainer rulings 2026-10-16 (#4018 activity 7261: every delegated policy is a requirement, verified at startup, failing closed) and 2026-10-18 (activity 7471: the operator installs and runs Postgres and pgvector; mnemra states its requirements and can verify them))

*Under the operator model, every policy the embedded design enforced by writing the cluster's configuration becomes a policy the host **delegates** to the operator. A delegated policy is not a hope: it is a requirement on the instance, stated here, verified by the host over its **serving role** on every start, on every retry and on every forced retry (R-0118), and failing closed — an unmet or unverifiable hard requirement means the host does not serve. What the host cannot verify is named, in one list the host itself emits, as the operator's (R-0117-j). Keystone anchors: **maintainer ruling 2026-10-16 (#4018 activity 7261, item 1)** — the ruling that every delegated policy is verified at startup and fails closed is the primary anchor, because no canon principle yet reaches runtime verification of a policy a product delegates to an external party (P-VerifyInheritedState covers agent handoffs; the canon gap is filed as #4050 and is not invented here); **V-Security** — default-on, no opt-in: a tenant boundary that depends on a role attribute nobody checked is not a boundary; **P-SecurityLayered** — a control that errors denies: an unverifiable requirement is reported, never assumed met; **P-GuaranteeByMechanism** — each requirement is carried by a check that fails loudly, never by an operator document alone. Verbatim, Peter 2026-10-16 (activity 7260): "when we defer required policy to an external entity we need to do due diligence."*

**Two roles (maintainer ruling 2026-10-19, #4018 activity 7771, confirming #3591 activity 7289).** The host uses two database roles, both created by the operator from `mnemra check-db --setup-sql` (R-0118-d): an **owner role** that owns every schema object and is used **only** by `mnemra init` under its own credential (R-0119-g), and a **serving role** that holds DML grants only, owns nothing, is not a member of the owner role (directly or transitively), and holds none of `SUPERUSER`, `BYPASSRLS`, `CREATEROLE`, `CREATEDB`, `REPLICATION`. The serving process never holds the owner credential. Every clause below is checked as the serving role; `mnemra init` additionally checks R-0117-a/-b/-d/-g/-i/-k/-l as the owner role before migrating.

**Classification (maintainer rulings 2026-10-19, activities 7761 and 7771).** **Every requirement in this block is hard at V0**: while unmet or unverifiable, the host does not serve — no MCP verb executes and readiness is false with the reason (R-0118-b). Each clause bears on the tenant boundary, on whether an acknowledged write is durable, on what leaves the host in server logs, or on the schema every verb runs against, and serving a partial result under any of them would mislead the caller (a write acknowledged against `fsync = off` reads as durable; a verb served under `BYPASSRLS` reads as isolated). **There is no soft class and no per-capability gating machinery at V0** (ruling 7771: "build it when needed"). The design for the first soft entrant is recorded once, in R-0118-i, with the mechanism that fires it.

- R-0117-a (server version): The host SHALL hold its supported major and its minor floor as code constants read by the check, and SHALL report `pg_version_unsupported` for any other major or any minor below the floor. The V0 major is `16` (the engine pin the embedded design carried, MEASURED `libs/mnemra-host/storage/postgres/engine.rs:216`, `EMBEDDED_PG_VERSION = "=16.4.0"` at `57cfeca`); the V0 minor floor is **`16.15`** (`server_version_num ≥ 160015`; released 2026-08-13, the latest 16.x at the time of measurement) — MEASURED by Sage 2026-10-19 from the PostgreSQL security page (`postgresql.org/support/security/`, 16.x filter), spot-checked by the lead: 55 CVEs affect 16.x, every one is fixed by 16.15, and 25 are fixed only in 16.15 — among them, all CVSS 8.8 per that page, CVE-2026-16239 (cursor type confusion → code execution), CVE-2026-14669 (`to_char` heap overflow), CVE-2026-14664 (regexp heap overflow), CVE-2026-15741 (deparse SQL injection), CVE-2026-14670 (plperl overflow); and, directly relevant to R-0117-e, CVE-2026-14666 (row-security caching disregards role modifications, 4.2). The floor is set from that history, not from a feature (maintainer ruling 2026-10-19, activity 7793, AE6). **Measured for the record:** the embedded engine's pin `=16.4.0` (`libs/mnemra-host/storage/postgres/engine.rs:216` at `57cfeca`) is exposed to 49 of the 55. **Floors move:** the next PostgreSQL minor is scheduled for 2026-11-12 (quarterly, published roadmap). The re-check is a **mechanism, not a cadence**: the weekly scheduled workflow of R-0120-c also resolves the latest 16.x minor from the PostgreSQL security page and the latest pgvector release from OSV, and fails when either exceeds the recorded floor — forcing the floor constant and this clause's label to be re-evaluated on the week a release lands, rather than on a reviewer's memory of the roadmap. The embedded engine never persisted a store, so no "compatible with stores initialised under the embedded engine" claim exists (Bolt M7). Widening the major set is an amendment to this clause. *(Binary-observable: against an instance at or above the floor the check reports `met`; against `15.x` it reports `unmet { pg_version_unsupported { found: 150004, supported_major: 16, minor_floor: … } }`; against `16.14`, below the `16.15` floor, it reports the same reason with `found: 160014`; in each unmet case the host does not serve.)* [P-GuaranteeByMechanism; V-Security — a minor floor is how known server-side fixes become a requirement rather than a hope; V-Consistency — one declared set, one check]
- R-0117-b (pgvector): The host SHALL verify, in the configured database, that the `vector` extension is installed at a version ≥ the floor held as a code constant — `extversion` compared **numerically, component by component** (major, minor, patch as integers; `0.8.10` > `0.8.7`, never a string comparison), and an `extversion` that does not parse to three integer components is `unverifiable { setting: "pgvector_version" }`, which is unmet — and SHALL NOT run `CREATE EXTENSION` on the operator's instance (that step needs a privilege neither host role holds; it is the operator's install per the 2026-10-18 ruling). The HNSW-introducing release P-0010 D2 requires (`0.5.0`) is far below the floor and affected by all three, so the feature bound is moot. **Measured for the record:** the embedded design's pgvector channel (`PGVECTOR_VERSION = "=0.16.105"`, `engine.rs:225-229` at `57cfeca`, the portalcorp build bundling pgvector 0.8.0) is exposed to all three, and that channel's newest tag bundles 0.8.0, so it **cannot reach the floor** — evidence carried to P-0010 DE1. The re-check mechanism is the one stated under R-0117-a. *(Binary-observable: a database without the extension reports `pgvector_missing` with guidance naming `CREATE EXTENSION vector` as the operator's step; one at a version below the floor reports `pgvector_version_unsupported`; `0.8.10` against the `0.8.7` floor reports `met` (numeric, not lexical); an `extversion` of `0.8.7-dev` or `latest` reports `unverifiable` and the host does not serve; the host issues no `CREATE EXTENSION` statement on any path — a SQL-observation seam over the host's statements shows none.)* [P-LeastAuthority — the host does not hold the privilege to install an extension; P-0010 D2]
- R-0117-c (serving-role attributes, ownership and membership): The serving role SHALL NOT be a superuser and SHALL NOT hold `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION` (`pg_roles` for `current_user`, first offending attribute reported); SHALL own no relation in the mnemra schema (`pg_class.relowner` joined to `pg_namespace`, first owned relation reported as `role_owns_relation`); and SHALL be a member of **no** other role, directly or transitively — the check evaluates `pg_has_role(current_user, oid, 'MEMBER')` over every row of `pg_roles` except `current_user` itself, against an allowlist that is **empty at V0**, so membership of the owner role, of `pg_execute_server_program`, `pg_read_server_files`, `pg_write_server_files`, `pg_read_all_data`, `pg_write_all_data`, `pg_signal_backend` or any other predefined or operator role reports `role_membership { role }`. Widening the allowlist is an amendment to this clause. **The serving role SHALL hold no `CREATE` privilege on any non-system schema** (`has_schema_privilege(current_user, n.oid, 'CREATE')` false for every `pg_namespace` row outside `pg_catalog`, `pg_toast`, `information_schema` and the per-session `pg_temp_N` / `pg_toast_temp_N` schemas — `public` included — reported as `role_schema_create { schema }`), **SHALL hold no `CREATE` on the database** (`has_database_privilege(current_user, current_database(), 'CREATE')` false, `role_database_create`), **and the mnemra schema's `nspowner` SHALL be the owner role** (`schema_owner_mismatch { schema, owner }` otherwise). Cause (Warden round 2): a cluster `pg_upgrade`d from PostgreSQL ≤ 14 keeps `CREATE` on `public` for `PUBLIC`, so a function planted through SQL injection as the serving role in a schema on the owner's `search_path` would run with owner authority at the next `mnemra init`; closing `CREATE` for the serving role and pinning the schema owner removes the planting surface, and R-0013-a's qualified `search_path` removes the lookup surface. `--setup-sql` therefore issues `REVOKE CREATE ON SCHEMA public FROM PUBLIC` and `CREATE SCHEMA mnemra AUTHORIZATION <owner>` (R-0118-d). These are the operational preconditions [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) records under "Multi-tenancy and the single-transaction supersession surface" (items 1 and 2), now verified rather than assumed, and the precondition #3591's RLS-in-V0 ruling (activity 7262) depends on. *(Binary-observable: connecting as a superuser reports `role_overprivileged { attribute: "superuser" }`; a role granted `BYPASSRLS` reports `attribute: "bypassrls"`; a role that owns one table in the mnemra schema reports `role_owns_relation { table }`; a role granted membership of the owner role, or of `pg_read_server_files`, reports `role_membership { role }` naming it; a role granted `CREATE` on `public` reports `role_schema_create { schema: "public" }`; a role granted `CREATE` on the database reports `role_database_create`; a mnemra schema owned by the serving role reports `schema_owner_mismatch` — **one seeded failing case per attribute, per the ownership rule, per listed predefined role, per `CREATE` rule and for the schema owner**; a role created `LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION` with DML grants only, no memberships and no `CREATE` anywhere, against a schema owned by the owner role, reports `met`.)* [P-LeastAuthority; V-Security; P-0010 multi-tenancy preconditions; #3591 ruling 7289]
- R-0117-d (durability settings, on the sessions writers use): At every check, on the check's **dedicated connection, opened new for that run and closed at its end** (R-0118-a) — with options identical to the serving pool's (same role, database, transport, `application_name`), so that a role- or database-level override is observed exactly as a freshly opened writer session would observe it; the check never borrows a pooled connection (independence from pool exhaustion) and never keeps a session across runs (a kept session would carry the defaults it was opened with) — `SHOW fsync` SHALL return `on`, `SHOW full_page_writes` SHALL return `on`, `SHOW synchronous_commit` SHALL return a value other than `off` (`local`, `on`, `remote_write` and `remote_apply` all flush the local WAL before a commit is acknowledged), and `SHOW data_sync_retry` SHALL return `off`. Because a pooled session that was opened before an operator changed a role-level default keeps its old value until it reconnects, the host SHALL rebuild the serving pool (close every idle connection; close each checked-out connection on return) on every unmet→met transition of this clause and on every `SIGHUP`, so that after a drift is corrected no writer session still carries the weakened value; and every pooled connection SHALL have a **maximum lifetime** code constant of `5 min` (R-0119-f), so a drift switched off and back on between two checks — invisible to the check, visible to the sessions opened in between — bounds the stale sessions to five minutes rather than the pool's life. The rebuild transient (old connections draining while new ones open) can briefly hold up to twice the pool size on the instance; R-0117-j item 4 counts it. The host SHALL NOT itself `SET` any of the four on any session, and SHALL NOT issue `ALTER ROLE … SET` or `ALTER DATABASE … SET` for them. This is the maintainer's 2026-10-18 correction (activity 7472) applied: the move to an operator instance does not close the persistence defect; the durability requirement is written here and verified. *(Binary-observable: a `test-hooks` injection that pre-opens a check connection and keeps it across runs is **not** what the check uses — after `ALTER ROLE <serving role> SET synchronous_commit = off` the next run opens a new connection and reports `unmet`, and `pg_stat_activity` shows the check's `application_name` session appearing and disappearing per run; with one pooled connection held checked-out across the drift, `ALTER ROLE <serving role> SET synchronous_commit = off` followed by a forced retry reports `unmet { durability_off { setting: "synchronous_commit", value: "off" } }` and readiness goes false; after `ALTER ROLE … RESET synchronous_commit` and `SIGHUP`, the check reports `met`, the held connection is closed on return rather than reused, and every connection the pool hands out afterwards shows `synchronous_commit` ≠ `off`; a SQL-observation seam shows the host never emits `SET fsync`, `SET synchronous_commit`, `SET full_page_writes` or `SET data_sync_retry`.)* [V-Reliability — correctness under failure is designed and measured; P-GuaranteeByMechanism — the host checks the effective value on the sessions that matter; P-CheckCoversTheClaim — the check is keyed on the sessions the claim is about]
- R-0117-e (row-level security forced, reconciled against the catalog): For every table in the schema's RLS manifest — the single-sourced, **schema-qualified** list of tenant-scoped tables the #3591 amendment defines (rulings 7262, 7289: one policy template, `tenant_id = current_setting('app.tenant_id')::uuid`, on every tenant-scoped table) — `relrowsecurity` and `relforcerowsecurity` SHALL both be true. The check SHALL join `pg_class` to `pg_namespace` on the manifest's `(schema, name)` pairs and SHALL require the found-count to equal the manifest length, so a dropped or renamed table reports `rls_manifest_mismatch { missing }` rather than passing by absence. The check SHALL also run the opt-out reconciliation: every table in the mnemra schema whose `pg_attribute` carries the tenant column SHALL be in the manifest, and any that is not reports `rls_manifest_mismatch { extra }`. `FORCE` is required because the owner role owns the tables and an owner bypasses its own policies unless forced ([P-0010](../src/adrs/P-0010-storage-substrate-engine.md) multi-tenancy precondition 2); under the two-role model (7771) the serving role is not the owner, so `FORCE` is defence in depth on the owner's `mnemra init` sessions, not the serving path's only fence. While the manifest is empty (before #3591 lands its policies) the clause reports `not_applicable (manifest_tables: 0)`, which is a reported zero and never a `met`; **the `not_applicable` state ends the moment the manifest is non-empty**, and a test SHALL assert that `not_applicable` never co-occurs with a non-empty manifest. This clause does not define the policies, the tenant key or the manifest: those are #3591's. *(Binary-observable: with a non-empty manifest, `ALTER TABLE <listed table> NO FORCE ROW LEVEL SECURITY` followed by a forced retry reports `rls_not_forced { table }`; `DROP TABLE <listed table>` reports `rls_manifest_mismatch { missing: [table] }`; a seeded table carrying the tenant column but absent from the manifest reports `rls_manifest_mismatch { extra: [table] }`; in each case the host stops serving; with an empty manifest the readiness body carries `R-0117-e: not_applicable (manifest_tables: 0)` and the co-occurrence test passes.)* [V-Security; P-TrustworthySignal — an enumeration that gates ships its reconciliation, opt-out polarity; #3591]
- R-0117-f (transport authentication and encryption, local included): Neither a loopback TCP connection nor a unix socket authenticates the server by itself, and the Postgres client library the host uses answers cleartext and MD5 password requests and offers no SCRAM channel binding (Warden, MEASURED in sqlx-postgres 0.9.0 `sasl.rs:14`, `establish.rs:74-98`). Therefore: (i) **a password SHALL only ever be sent over a TCP connection with `sslmode = verify-full`** against the operator-supplied CA — loopback included — and the host SHALL refuse, before connecting, any configuration that would send a password otherwise (`config_rejected { reason: "password_without_tls" }`, R-0119-d); after connecting it SHALL verify its own backend reports `ssl = true` in `pg_stat_ssl` (`transport_unencrypted` otherwise); (ii) **a unix socket SHALL be used only with peer authentication and no password**, and before the first byte is sent the host SHALL read the peer's uid (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` / `getpeereid` on macOS) and require it to equal the owner uid of the socket directory, and require the socket directory to carry **no group and no other write bit** (no sticky exception: a world-writable sticky directory such as `/tmp` is root-owned, and Postgres never runs as root, so the owner-uid match fails there by construction — the operator's socket directory is the fix, and the `guidance` names it) — a mismatch reports `transport_unauthenticated { reason }` and no bytes are sent. *Residual, labelled: a parent directory of the socket directory that others can write lets another uid rename the directory away and plant one of its own; the check does not walk ancestors, and the deployment document tells the operator to place the socket directory under a root-owned, non-writable path (the distribution default `/var/run/postgresql` is one).* **"On the same connection, before the first byte" is an implementation-time mechanism**: the client library writes the startup packet itself with no pre-write hook (Warden, MEASURED in sqlx-postgres 0.9.0), so until the host opens the socket itself and hands the connected descriptor to the driver, or the driver exposes a hook, the check runs on a separate pre-connection to the same socket path immediately before the driver connects; the same-connection form is pinned by the expected-failure test of R-0120-h; (iii) a hostname — `localhost` included — is never treated as local: the host does not resolve names to decide security posture. **Refusing a cleartext or MD5 authentication request from the server is an implementation-time question**: the client library exposes no option for it today, so this amendment records the requirement (the host SHALL NOT answer an `AuthenticationCleartextPassword` or `AuthenticationMD5Password` request) and names the gap; until the mechanism exists, (i) bounds the exposure to a server whose identity `verify-full` has established, and R-0117-k plus the `pg_hba` obligation (R-0117-j item 6) keep the server from asking. Both implementation-time mechanisms are pinned as **expected failures with a named exit condition, visible in the gate output** (R-0120-h) — never a silently excluded or `#[ignore]`d test, and never a red gate. *(Binary-observable: `postgres://u@127.0.0.1/m` with a password file is refused with `password_without_tls`; `postgres://u@127.0.0.1/m?sslmode=verify-full&sslrootcert=/path` with a password file connects and reports `met` iff `pg_stat_ssl.ssl` is true; `postgres://u@/m?host=/var/run/postgresql` with no password file connects, and a test that pre-creates a socket in a directory owned by another uid observes `transport_unauthenticated` and zero bytes written; a seeded fake server that sends `AuthenticationCleartextPassword` is the pinned negative case for the implementation-time mechanism, recorded as `#[ignore]`-free and failing until the mechanism lands.)* [V-Security — default-on; P-SecurityLayered — the control fails closed on configuration, before the network; maintainer ruling 7771 (local server spoofing is not an accepted risk)]
- R-0117-g (encoding): `SHOW server_encoding` SHALL return `UTF8`; JSONB frontmatter and text bodies are stored as UTF-8 and a differently encoded database rejects or transcodes them. *(Binary-observable: a `LATIN1` database reports `encoding_unsupported { found: "LATIN1" }`.)* [V-Quality; R-0001-a]
- R-0117-h (schema version; upgrades and their way back): The host SHALL compare the migrations recorded as applied in the configured database with the migrations the binary carries. All applied and none unknown → `met`; no migrations table → `schema_missing` (guidance: run `mnemra init`); binary carries unapplied migrations → `schema_pending_migrations { count }` (guidance: run `mnemra init --dry-run`, then `mnemra init`); database records a migration the binary does not carry → `schema_newer_than_binary { found, expected }` (guidance: run the newer binary, or **restore the pre-migration backup** — there is no downgrade path). **The host's start SHALL NOT apply migrations**; `mnemra init` is the only path that does (R-0013-a as amended), so an operator upgrade is an explicit step with its own exit status, never a side effect of a restart. `mnemra init --dry-run` SHALL list the pending migrations with their names and print the backup warning (R-0013-d: a verified backup before any destructive migration; the way back after a migration is restore-from-backup) without changing anything. `mnemra init` SHALL take a transaction-scoped advisory lock on a host-wide constant key (`pg_advisory_xact_lock`) around the migration run and SHALL exit `3` with `init_in_progress` when the lock is held by another session, so two concurrent `init`s cannot interleave. **Rolling or blue-green upgrades — two binary versions serving one database at once — are not supported at V0**: the newer binary's migrations make the older host not ready (`schema_newer_than_binary`), which is the stated behaviour, not a defect. *Rejected alternative, kept for the record: forward-only auto-migration at host start. It makes a restart a schema-changing operation on operator-held data with no operator action and no distinct exit status, and it races two hosts started against one instance; the explicit step costs one command and keeps R-0013-d's "verified pre-migration backup" an operator decision rather than a startup side effect.* *(Binary-observable: a fresh database reports `schema_missing` and the host does not serve; `mnemra init --dry-run` against it lists every migration and exits `0` with the database byte-unchanged; after `mnemra init` the same host, on its next retry, reports `met` without a restart; a database migrated by a newer binary reports `schema_newer_than_binary` and the older host does not serve; two `mnemra init` processes started together end with one exit `0` and one exit `3`, and the migrations table holds each migration once.)* [V-Reversibility — the way back (restore from backup) is named before commit, and it is the true one; R-0013-d; P-LeastAuthority applied to actions — a restart holds no migration authority]
- R-0117-i (reachability, with bounded timeouts and hysteresis): The check SHALL attempt a connection with the configured options under a **connect timeout** code constant (`5 s`) and classify the failure: `unreachable` (no TCP/socket connection within the timeout), `auth_failed` (authentication rejected), `connect_denied` (no `CONNECT` privilege on the database). The `detail` field SHALL carry the driver's error class, never the URL's credentials (R-0004-h). **Hysteresis applies to this clause only, and it applies at first ready too**: one failed probe takes it `unmet` immediately; it becomes `met` only after **two consecutive** successful checks — the boot check counting as the first, so a host that comes up against a healthy instance is ready after the boot check plus one scheduled check (1 s later at the backoff floor), and a flapping instance does not flap readiness at the probe rate. The `auth_failed` reason SHALL use a longer backoff cap (`300 s`, R-0118-c) so a wrong credential does not hammer the instance's authentication log or trip a lockout. *(Binary-observable: with the instance stopped the check reports `unreachable` within 5 s of its start; with a wrong password file `auth_failed`; with `REVOKE CONNECT` `connect_denied`; in each case readiness is `503` with that reason and the process is still alive; after the instance returns, readiness flips to `200` on the second consecutive `met`, not the first.)* [V-Reliability — timeouts and graceful degradation are the standing patterns; V-Observability — the reason is machine-readable]
- R-0117-k (password hashing): `SHOW password_encryption` SHALL return `scram-sha-256`, so that any password the operator sets or rotates for either role is stored as SCRAM and the server never asks the host for an MD5 or cleartext response for a freshly set password. Whether an **existing** password hash is SCRAM is not readable by the serving role (`pg_authid` is superuser-only) and is therefore the operator's (R-0117-j item 7); `--setup-sql` sets passwords through the client-side `\password` path (R-0118-d), which hashes with the server's current `password_encryption`. *(Binary-observable: an instance with `password_encryption = md5` reports `password_encryption_weak { found: "md5" }` and the host does not serve.)* [V-Security; P-SecurityLayered — a design-time ban on MD5 carried as a runtime check]
- R-0117-l (server-side parameter logging): R-0004-h (no artifact bodies, content fragments or raw query strings in any emitted record) is now delegated for the half the server writes. The host binds every content value as a query parameter (never inlined as a literal — a host-side requirement observable with the SQL-observation seam), so the server's statement text carries placeholders only; what the host can close from its side is **parameter** logging. Therefore `SHOW log_parameter_max_length` SHALL return `0` and `SHOW log_parameter_max_length_on_error` SHALL return `0`; `log_statement` and `log_min_duration_statement` are the operator's to set, because with parameter logging off they expose statement shapes, not content. **The claim is narrow**: this clause closes parameter logging; it does not close error `DETAIL` lines — at the default `log_error_verbosity` a constraint violation logs the failing row's values ("Failing row contains …"; INFERRED from the PostgreSQL documentation, not measured) — which is R-0117-j item 12, the operator's, because forcing `log_error_verbosity = terse` as a hard clause would take every operator's diagnostics away for a leak class the host can also shrink by validating before it writes. *Readability note: the four `log_*` GUCs and `password_encryption` are not flagged superuser-only to read in PostgreSQL 16 to the author's knowledge — INFERRED, not measured; the integration test of the probe measures it, and an unreadable hard GUC is `unverifiable`, which is `unmet` (R-0118-a).* *(Binary-observable: `ALTER ROLE <serving role> SET log_parameter_max_length = -1` followed by a forced retry reports `parameter_logging_on { setting: "log_parameter_max_length", value: "-1" }` and the host stops serving; a SQL-observation seam shows no content literal in any statement the host emits.)* [R-0004-h; V-DataMinimization; P-GuaranteeByMechanism]
- R-0117-j (operator obligations the host cannot verify — **NOT VERIFIED BY MNEMRA**): The host SHALL hold the obligations list as a single code constant, SHALL print it from `mnemra check-db --obligations` (R-0118-d) with the heading "Not verified by mnemra — the operator's", and the operator deployment document (Constraints, "Operator-run instance") SHALL carry the same list verbatim; a docs test SHALL assert the document's list equals the binary's. V0 list: (1) the instance's data directory is on persistent storage — never a container's writable layer or a temporary directory — and whether it is local or network-backed is the operator's choice (the brief's Hard constraint "Data lives outside the executable and its image", maintainer ruling 2026-09-15, now binding on the operator's instance); (2) **backups and point-in-time recovery, NOT VERIFIED BY MNEMRA**, including a verified restore before any migration (R-0013-d) — restore-from-backup is the only way back after `mnemra init`; (3) the supply chain of the Postgres and pgvector install — OS packages from the distribution's or PostgreSQL's signed repositories, or an image pinned by digest — **this is a loss relative to the embedded design, which hash-pinned the binaries it ran (`KNOWN_GOOD_HASHES`, `libs/mnemra-host/storage/postgres/engine.rs:306` at `57cfeca`); ### R-0118 — Startup check, readiness and liveness are three contracts; the host stays up, refuses to serve, retries, and reports why (Amended 2026-10-19, #4018; anchors [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) §Amendment 2026-10-19, the [observability baseline](../src/architecture/overview.md#observability); maintainer ruling 2026-10-19 (#4018 activity 7749))

*Verbatim, Peter 2026-10-19: "i've had arguments from developers before on crashing in k8s being the correct answer, k8s keeps trying to restart wihch is dumb. better answer is the health check indicates it can't run and why with a way to ensure it occasionally trys again or is forced to try again"; and "staying up only works if it doesn't serve, that IMO is obvious"; and "service readiness, startup checks are separate from health checks, i think they are different things … people merge them all together." This requirement is written to those three statements. The first two are rulings; the third is a stated view the amendment designs to (P-0010 §Amendment AE1; the 2026-10-19 rulings 7761 and 7762 presuppose the readiness surface and did not object to the split). Reading applied, not ruled: this refines the 2026-10-16 "verified at startup and fails closed" ruling rather than reversing it — fail closed means refuse to serve, not exit. Keystone anchors: **V-Reliability** — how the surface behaves when a dependency fails is designed, and the standing pattern is retry with backoff and graceful degradation; **V-Observability** — the instrument reports the reason, and a result it cannot produce is reported as such, and an instrument that stops reporting silently is worse than none; **P-ReliabilityTarget** — the readiness indicator is read from the consumer's side (can a call be served), not from the process's own view of itself.*

**Supported platforms (carried from R-0116-b, which this amendment retires):** Linux and macOS. No Windows: the forced-retry trigger is a Unix signal (R-0118-d), peer authentication reads Unix socket credentials (R-0117-f), and the credential file's protection is a Unix mode and owner (R-0119-b).

- R-0118-a (the instance check, one implementation, bounded and supervised): The host SHALL implement the R-0117 clauses as **one check** — a pure decision over an `InstanceFacts` record that a probe fills from the connection (P-TestableByDesign: the decision is unit-testable over injected facts; the probe is integration-tested against the real instance). The probe SHALL connect on its **own dedicated connection, opened fresh for each run and closed when the run ends** — never a persistent check session (one would keep the role-level defaults it was opened with and miss an `ALTER ROLE … SET`, the round-1 drift defect moved onto the check itself) and never a connection borrowed from the serving pool — opened with **exactly the options the serving pool uses** (R-0119-a), as the serving role and no other — there is no superuser or secondary credential for it (P-LeastAuthority); the dedicated connection is the "+ 1" of the connection budget (R-0119-f). Each clause's result is one of `met`, `unmet { reason }`, `unverifiable { setting, error }` (the role could not read what it needed: a `SHOW` or catalog read was denied, failed, or did not answer within the deadline) or `not_applicable { why }`. **`unverifiable` on a hard clause SHALL be treated as `unmet`** — the host never assumes a value it could not read. The whole check runs under a **per-check deadline** code constant (`10 s`, above the `5 s` connect timeout of R-0117-i); a check that overruns yields `unverifiable { setting: "check", error: "deadline" }` for every clause not yet decided. The check runs in a **supervised task**: a panic or an abort of the task restarts it and records one synthetic result with every clause `unverifiable { error: "check_task_restarted" }`, so a dead checker can never leave a stale `met` in place. The check runs at boot before readiness is granted, on the R-0118-c schedule, on every forced retry (R-0118-d) and on an observed pool error (R-0118-m, `trigger: "error"`). **Backoff is measured from the completion of the previous run**, never from its start. A `SIGHUP` arriving while a check is in flight SHALL NOT start a second concurrent check: it is **coalesced** into exactly one re-run that starts when the in-flight run completes. Every run SHALL emit one structured record `instance_check { run_at, completed_at, trigger: "boot" | "schedule" | "signal" | "error" | "cli", results: [ { clause, status, detail?, guidance? } ] }` on the host's structured-log sink (stderr today, `cmd/mnemra/logging.rs`; R-0004-d's "stdout" wording is a pre-existing divergence recorded in the R-0116 plan as SG-1; its tracker task is listed in P-0010 §Amendment, "Follow-ups"). *(Binary-observable: a unit test over injected facts produces one failing and one passing case per clause; an injected `SHOW` permission error on `fsync` yields `unverifiable` and the host does not serve; a `test-hooks` injection that parks the probe past 10 s yields `unverifiable { error: "deadline" }` and readiness `503`; a `test-hooks` injection that panics the check task produces the `check_task_restarted` record and a subsequent normal run; two `SIGHUP`s delivered during one in-flight check produce exactly one additional `trigger: "signal"` record; the record is emitted once per run with the stated `trigger` and `completed_at` ≥ `run_at`.)* [P-SecurityLayered — a control that errors denies; V-Observability — inconclusive is reported as inconclusive, and a silent stop is detected; V-Reliability — timeouts are the standing pattern; P-TestableByDesign]
- R-0118-b (an unmet hard requirement does not exit the process; the one deliberate exit): When any hard clause is `unmet` or `unverifiable`, the host SHALL stay up with the `/health` listener answering, SHALL set readiness false (R-0118-f), SHALL serve no MCP verb (R-0118-h), and SHALL keep retrying (R-0118-c). The host SHALL NOT call `exit`, panic, or return from `run()` because of an instance-check result. This holds equally for a connection that is not configured at all (`connection_not_configured`), for a refused configuration (R-0119, `config_rejected`), and — **maintainer ruling 2026-10-19, activity 7762** — for a database password file with a bad mode or owner (`credential_file_rejected`, R-0119-b): the host comes up, reports the reason and the remedy, and waits. **No operator override** of a hard refusal exists (no `--insecure`, no `MNEMRA_SKIP_CHECKS`): a bypass is the control failing open on request, and the stay-up posture already gives the operator the time to fix the instance instead. The **one deliberate exit** on the startup path is a failed bind of the `/health` + `/ready` listener (`MNEMRA_HEALTH_PORT` in use or unbindable): with no probe surface there is nothing to report through, so the host exits non-zero naming the port — stated here so it is not read as an oversight. The `SIGHUP` handler SHALL be installed **before** the listener binds, so no window exists in which the probe surface is up and the forced retry is not. The host's three pre-existing own-file refusals (the admin-token, signing-material and LLM-key mode checks — R-0005-f / R-0008-e / R-0014-d, the "5-pre" boundary) **remain exits in this amendment** (maintainer ruling 2026-10-19, activity 7761: "later, as a follow-up"); the follow-up that moves them to the stay-up posture is a tracker task Puck files as a blocking dependency of the container-image work (P-0010 §Amendment, "Follow-ups"), because the Secret-mount default that makes an exit crash-loop is a container fact. *(Binary-observable: `mnemra` spawned with `MNEMRA_DATABASE_URL` pointing at a stopped instance is still running 60 s later, `GET /health` returns `200`, `GET /ready` returns `503` with `reasons: [{ clause: "R-0117-i", reason: "unreachable" }]`; starting the instance then causes `GET /ready` to return `200` within one retry interval plus one check duration with no host restart; a password file at mode `0644` yields `503` with `reason: "credential_file_rejected"` and a `guidance` naming `chmod 0600` and the Kubernetes `defaultMode`, not an exit; `mnemra` spawned with `MNEMRA_HEALTH_PORT` already bound exits non-zero naming the port; the binary accepts no flag or variable that skips a clause — `mnemra --help` lists none and a seeded `MNEMRA_SKIP_CHECKS=1` changes nothing.)* [maintainer rulings 2026-10-19 (7749, 7761, 7762); V-Reliability — graceful degradation over crash-restart; P-SecurityLayered — no bypass of a control]
- R-0118-c (retry schedule): While any hard clause is unmet, the host SHALL re-run the check with exponential backoff: first retry 1 s after the failing run **completes**, doubling, capped at 30 s — except that while the only unmet clause is R-0117-i with reason `auth_failed` the cap is 300 s — with no attempt limit. Once every hard clause is met, the host SHALL re-run the check every 30 s to detect drift; a drift to unmet SHALL take readiness false and stop serving within one interval plus one check duration (R-0118-h), and the backoff schedule restarts. The R-0117-i two-consecutive-successes hysteresis applies on the way back up. The intervals are code constants, not operator configuration, at V0. *Rejected: a fixed interval (no backoff) — V-Reliability names retry with backoff as the standing pattern, and a 1 s floor gives a just-started instance a fast first success while the 30 s cap bounds the load on a shared instance; an attempt limit — ruled out by the stay-up ruling; re-checking on every readiness probe — couples check load to probe cadence an orchestrator sets, and a probe is a read, never a trigger.* *(Binary-observable: with the instance down, the `instance_check` records are spaced 1, 2, 4, 8, 16, 30, 30, … seconds (±10 %) between `completed_at` and the next `run_at`, with `trigger: "schedule"`; with a wrong password the spacing reaches and holds at 300 s; with the instance up, records are spaced 30 s; `ALTER ROLE … SET synchronous_commit = off` is reflected as `ready: false` within 30 s plus one check duration.)* [V-Reliability — retries with backoff; V-Simplicity — three constants, no configuration surface]
- R-0118-d (forced retry and the operator verbs): The forced-retry trigger is **`SIGHUP`** to the host process: on `SIGHUP` the host SHALL re-read the R-0119 password file, re-run the check (coalesced per R-0118-a) with `trigger: "signal"`, rebuild the serving pool (R-0117-d), and reset the backoff. The admin CLI SHALL expose three verbs with distinct jobs. **`mnemra check-db` is the operator's pre-flight and nothing else** — never a probe body: it runs the same check (R-0118-a) **out-of-process** against the configured instance as the serving role, prints the per-clause results and the obligations in human-readable form, and exits by precedence `2` (any clause unverifiable, or the instance unreachable) over `1` (any clause unmet) over `0` (every hard clause met); it does not signal the running host. `mnemra check-db --setup-sql` prints the SQL an operator applies once with their own privileges: `CREATE ROLE` for the owner role and the serving role with the R-0117-c attribute set, the database, `REVOKE CREATE ON SCHEMA public FROM PUBLIC`, `CREATE SCHEMA mnemra AUTHORIZATION <owner>`, `GRANT CONNECT` (and no `CREATE` on the database) to both, `GRANT USAGE` on the mnemra schema to both (and `CREATE` to neither — the owner creates by ownership), `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA` plus the matching `ALTER DEFAULT PRIVILEGES FOR ROLE <owner>` to the serving role, the [P-0020](../src/adrs/P-0020-report-execution-context.md) report role when the reporting engine is enabled — and **no password literal**: each role is created `PASSWORD NULL` and the output ends with the instruction to set each password through `psql`'s `\password <role>`, which hashes client-side under `password_encryption` (R-0117-k) so no secret lands in SQL history or server logs. `mnemra check-db --obligations` prints the R-0117-j list. `mnemra ready` wraps `GET /ready` and `mnemra health` wraps `GET /health`: each reads `MNEMRA_HEALTH_PORT`, uses its own client timeout code constant (`2 s`, below the probe timeout the deployment document tells an orchestrator to set, `≥ 3 s`), and exits `0` on `200`, `1` on `503`, `2` when the listener refuses the connection or does not answer within the timeout — so an orchestrator can tell "not ready" from "no listener". *Rejected: a `POST /ready/recheck` route on the loopback listener — it adds a mutating route to a listener R-0004-g makes `GET`-only and unauthenticated, and a mutating unauthenticated route is a control surface the design has no reason to open; an admin-token-gated HTTP endpoint — no admin HTTP surface exists at V0 and control-plane operations route through the CLI (R-0010-g); making `check-db` signal the host — it would couple an out-of-process verb to process discovery, and `kill -HUP` already exists on every supported platform; passwords in the setup SQL — they would sit in `psql` history, the operator's shell history and the server log.* *(Binary-observable: `kill -HUP <pid>` produces an `instance_check` record with `trigger: "signal"` within 1 s of the in-flight check completing, regardless of the backoff position; `mnemra check-db` against a superuser URL prints `R-0117-c unmet role_overprivileged { attribute: "superuser" }` and exits `1`; against a stopped instance it exits `2`; against a stopped instance with the superuser URL it still exits `2` (precedence); `--setup-sql` output contains no `PASSWORD '` literal, and applied by a superuser to a fresh instance followed by `\password` for both roles yields a serving role for which `check-db` reports `R-0117-c met`; `mnemra ready` with no listener bound exits `2` within 2 s; with a `503` it exits `1`.)* [V-Simplicity — one signal, no new surface; P-LeastAuthority — the only principal that can force a retry is one that can already signal the process; V-Security — no secret in SQL history; R-0010-g]
- R-0118-e (liveness, `GET /health`): `GET /health` SHALL answer the question "is the process alive and not wedged" and nothing else: `200 { "alive": true, "pid", "uptime_s" }` when the host's main async runtime answers an in-process ping within 1 s, `503 { "alive": false }` otherwise. The handler SHALL run on a thread that is **not** the async runtime (the listener already has its own thread, `libs/mnemra-host/health.rs`), send the ping into the runtime, and wait with a `recv_timeout` of 1 s, so a wedged runtime is observed rather than waited on. It SHALL NOT open a connection to the instance, read the check results, or depend on readiness in any way, so an instance outage of any length cannot turn it `503`. **The implication between the two is one-directional by design: `ready` ⇒ `alive`, never the reverse.** `/health` `200` with `/ready` `503` is the normal not-ready state (the process is fine, the instance or its configuration is not); `/ready` `200` with `/health` `503` cannot occur, because a runtime that does not answer the liveness ping cannot have completed a check or be serving. The maintainer asked at the gate whether health can be good while ready is not (activity 7787); the answer is yes, and it is the designed state. An orchestrator's **liveness probe** points here, and its **startup probe**, if any, points here too — a startup probe on readiness would fail for the whole of an instance outage at boot and reach the orchestrator's restart threshold, which is the loop this requirement prevents. **Stated honestly: a startup probe on `/health` verifies only that the listener bound and the runtime answers; the real start-up signal is the first completed instance check**, visible as the first `instance_check` record and as `last_run_at` becoming non-null in `/ready` (R-0118-f). *(Binary-observable: with the instance stopped for ten minutes, `GET /health` returns `200` on every probe; with the host's runtime deliberately blocked (a `test-hooks` injection that parks the runtime), `GET /health` returns `503 { "alive": false }` within 1 s and the listener thread is still answering; a SQL-observation seam shows no statement issued by the `/health` handler.)* [V-Reliability; P-CheckCoversTheClaim — liveness checks liveness; the restart-loop ruling]
- R-0118-f (readiness, `GET /ready`): `GET /ready` SHALL answer "can the host serve a call right now": `200 { "ready": true, "last_run_at", "age_s", "checks": [ … ] }` iff every hard clause of the most recent **completed** check is `met` (or `not_applicable` where this requirement permits it — see below), that check completed no longer ago than the **staleness bound**, where the `checks` entry for R-0117-f (and any clause with an open R-0120-h entry) carries `known_gaps: [ <XFAIL names> ]` generated from the single-sourced XFAIL list — so an operator reading `met` on R-0117-f also reads that two spoofing mechanisms are known failures while they are; `mnemra check-db` prints the same list under the clause — **and** the MCP server is accepting requests (the `mark_ready` gate); otherwise `503 { "ready": false, "reasons": [ { clause, status, reason, detail?, guidance? } ], "next_retry_s", "last_run_at", "age_s", "checks": [ … ] }`. **The staleness bound is derived from the current schedule, not a fixed number**: 2 × the current scheduled interval + the 10 s deadline — 70 s while serving at the 30 s cadence, and 2 × the current backoff + 10 s while not ready, so a 300 s `auth_failed` backoff (R-0118-c) is not masked by a `stale_check` and the operator keeps seeing the true reason. A check older than the bound is the `stale_check` reason: the checker has stopped reporting and readiness is withdrawn rather than carried on a stale `met`. **`not_applicable` is permitted on exactly two clauses** — R-0117-e while the RLS manifest is empty, and the P-0020 report-role presence check while the reporting engine is disabled (R-0013-e as amended); a `not_applicable` on any other clause is a check defect and SHALL be treated as `unmet { reason: "unexpected_not_applicable" }`. The body carries the full most-recent `instance_check` results under `checks`, so an operator reads one endpoint for the why; **detailed reasons appear here and on `mnemra check-db` only** (both loopback-or-local), never on the MCP surface (R-0118-h). During a graceful drain (SIGTERM received) readiness is `503 { "ready": false, "reasons": [ { "reason": "draining" } ] }` while `/health` stays `200` until exit (R-0118-l). An orchestrator's **readiness probe** points here. `ready` ⇒ `alive` always (a `200` here implies `/health` is `200`); the converse never holds (R-0118-e). The listener stays loopback-only (R-0004-g), so at V0 an orchestrator reaches both probes by **exec** (`mnemra health`, `mnemra ready`), not by HTTP from outside the pod; the non-loopback bind, and the status-code-only response to unauthenticated callers it would require, is R-0004-g's existing tripwire, re-stated as a deferral in Out of Scope. **The status code is a function of the clause statuses and nothing else**: a property test SHALL drive the route over every combination of clause status (`met`, `unmet`, `unverifiable`, `not_applicable`), staleness and the `mark_ready` gate, and assert `200` iff all hard clauses are `met` (or `not_applicable` on exactly the two permitted clauses), fresh under the schedule-derived bound, and the gate is open — seeded with the embedded-era defect (`libs/mnemra-host/health.rs:627-629` at `57cfeca` returned `200` for `overall: "down"`) and with a `not_applicable` on a non-permitted clause as the pinned failing cases. *(Binary-observable: before `mark_ready`, `503` with `reason: "starting"` and `last_run_at: null`; after, with all hard met, `200 { "ready": true, "age_s": < 70 }`; with R-0117-i unmet, `503` whose `reasons[0].clause` is `"R-0117-i"` and whose `next_retry_s` equals the current backoff; **with a wrong password held for 120 s, every `GET /ready` in that window returns `503` with `reasons[0].reason = "auth_failed"` and never `"stale_check"`**; with the checker parked by a `test-hooks` injection for 80 s while serving, `503` with `reason: "stale_check"` and `age_s ≥ 70`; after SIGTERM, `503` with `"draining"`; the property test passes and fails on both seeded cases; `checks[R-0117-f].known_gaps` is non-empty exactly when the XFAIL list is non-empty — a test seeds an empty list and asserts the key is `[]`, and seeds one entry and asserts it is named.)* [P-ReliabilityTarget — the indicator is read from the consumer's side; V-Observability — the why is machine-readable and a missing signal is detected; P-TrustworthySignal]
- R-0118-g (probe mapping, stated once): liveness probe → `GET /health` (exec `mnemra health`); readiness probe → `GET /ready` (exec `mnemra ready`); startup probe → `GET /health` or none, never `/ready`; pre-flight before first start, and the operator's diagnostic when `/ready` says no → `mnemra check-db` (never wired as a probe: it opens its own connection and runs the full check, which is the wrong cost and the wrong semantics for a probe cadence). If two of these contracts share an implementation, the shared part is the `InstanceFacts` probe and the check (R-0118-a); the three surfaces SHALL stay distinct in route, body and semantics, because merging them is exactly what makes a database outage restart a process. *(Binary-observable: the operator deployment document carries this mapping verbatim and the docs test of R-0117-j covers it.)* [V-Consistency — the same question gets the same endpoint across deployments]
- R-0118-h (MCP on stdio while not ready — coarse code, no detail): While readiness is false, the MCP server SHALL still complete `initialize` and answer `tools/list` (so a client sees a live server and the verbs it will have), and SHALL answer every `tools/call` and every other verb-dispatching request with the structured JSON-RPC error `host_not_ready` (custom code; API Contract error table) whose `data` carries **only** `kind: "not_ready" | "draining"` and `next_retry_s`. It SHALL NOT carry the clause list, reasons, details or guidance: while the instance is unreachable the token lookup (`admin_tokens`, in the database) cannot run, so every stdio caller is **unauthenticated** at that moment, and an unauthenticated caller learns nothing about the instance's configuration from the error; the detailed reasons live on `GET /ready` (loopback) and `mnemra check-db` (local), R-0118-f, and the error's `data` carries a fixed `hint: "run mnemra ready or mnemra check-db on the host"` so an operator reading a client log knows where to look. **Reconciliation with R-0010-c** (`DF-auth-check` on every incoming request before routing to any builtin or plugin handler): while not ready, `initialize` and `tools/list` are answered from the server's static state (protocol capabilities and the manifest-declared verb names, which are public in the repository's signed manifests) **without routing to any builtin or plugin handler**, and every other request is refused with `host_not_ready` **before** routing; so no request reaches a handler without the auth check, and R-0010-c's "before routing" clause holds — the two protocol requests are not routed at all. R-0010-c carries an amendment note to this effect. No host-fn executes, no `WorkspaceCtx` is constructed for the call, and no plugin instance is invoked. The host SHALL NOT close the stdio transport or exit because readiness is false: a client that treats a closed transport as a dead server re-spawns the host, which is the stdio form of the restart loop. *(Binary-observable: a client connected over stdio to a host whose instance is down completes `initialize`, receives a `tools/list` naming `echo.create`, and receives `host_not_ready` with `data = { kind: "not_ready", next_retry_s }` and no other key on `echo.create`; the same client, without reconnecting, receives a success on `echo.create` within one retry interval plus the hysteresis of the instance coming up.)* [maintainer ruling 2026-10-19; R-0010-f — error classes are distinguishable; V-Security — no configuration detail to an unauthenticated caller; V-Reliability]
- R-0118-i (no soft class at V0; the first entrant's design, with the mechanism that fires it): **No soft class, no `capability_unavailable` error, no `degraded` field, gate or test exists at V0** (maintainer ruling 2026-10-19, activity 7771: "build it when needed"). Recorded once, as design content for the first soft entrant and not as a contract: a soft clause would declare, in the R-0117 table, the closed set of capabilities it gates (MCP verbs, host-fns or subsystems by name); on drift those capabilities would refuse with a structured error naming the clause and reason while everything else serves, and readiness would report `200` with a `degraded` list naming them; a clause whose capability set cannot be stated stays hard. The first expected entrant is R-0117-b (pgvector), gating the embedding-write and dense-retrieval capabilities, once the retrieval cluster's degraded-mode matrix ([P-0014](../src/adrs/P-0014-retrieval-architecture.md)) is live. **What fires the decision** (P-Defer DF1, at the last cheap point): a test in the migrations suite SHALL fail when a migration introduces the first column of type `vector` while R-0117-b is still classified hard with no capability set — the failing test names this clause and forces the classification before the column lands. *(Binary-observable: no V0 verb returns an error naming a soft clause; `GET /ready`'s `200` body carries no `degraded` key; the migrations-suite test fails on a seeded `ALTER TABLE … ADD COLUMN embedding vector(1536)` and passes without it.)* [maintainer ruling 7771; P-Defer DF1 — the trip-wire is a test that fires on the migration, not a memory; V-Simplicity]
- R-0118-j (not-ready is visible: metrics, alert, log hygiene): The host SHALL emit, on the R-0004 OTel surface, the gauge `host_ready` (`1`/`0`) with a `clause` label naming the first unmet clause (or `none`), the counter `instance_check_total{trigger, status}` (one increment per run, `status ∈ { met, unmet, unverifiable }` for the run as a whole), the histogram `instance_check_duration_seconds`, and the gauge `seconds_since_last_ok`. - R-0118-k (supervision models and stdin): At V0 the only MCP transport is stdio (R-0010-a/-e), so the host is **always a child of the agent session that spawned it**: stdin EOF is a clean stop (R-0121-a), SIGTERM is a clean stop, the agent's process supervisor is the host's supervisor, and the exec probes are run by whatever manages that session. **A daemon model — the host under systemd, docker or Kubernetes with no stdio client — has no transport to serve at V0 and is therefore not supported**, stated here so the container snippets in the deployment document are read as "the operator's Postgres plus a stdio host", not as a service unit. The daemon model's design content is recorded for the **HTTPS shared-service transport amendment, tracker #4127** (maintainer rulings 2026-10-19, activities 7787–7790: one long-running mnemra service that every agent session reaches over streamable-HTTP MCP, HTTPS/TLS only, localhost included, one code path local and remote — "change the model so its acts like remote even when local"; it amends R-0010-a/-e, which stay as written in this amendment). #4127 is the trigger — a filed task, the next amendment, not a generic future event: the daemon's stop is SIGTERM only and stdin EOF SHALL NOT exit it; `sd_notify` `READY=1` is sent on the first completed check with every hard clause met and `WATCHDOG=1` is fed from the liveness ping (so a wedged runtime stops feeding it); `ExecReload=kill -HUP $MAINPID`; `Restart=on-failure` is safe only because a not-ready host exits `0` on SIGTERM and never on a check result; readiness for a unit without `sd_notify` is `ExecStartPost` polling `mnemra ready`. - R-0118-l (graceful drain): On SIGTERM or stdin EOF the host SHALL: mark readiness `503 { "draining" }` at once (R-0118-f); answer every new verb-dispatching request with `host_not_ready { kind: "draining" }` (R-0118-h); let in-flight verbs complete up to a **drain deadline** code constant of `10 s` (below the 30 s interval), after which each still-running verb is cut and recorded as R-0004-a `outcome = "error"`; ignore `SIGHUP` during the drain; cancel an in-flight instance check and start no new one; close the serving pool; and exit `0` when every in-flight verb completed, non-zero when the deadline cut any. A **second SIGTERM** during the drain SHALL exit immediately, non-zero. `/health` stays `200` until exit. The embedded-era `/health` drain scenario in this spec ("`/health` degraded and down states") is superseded by this clause. *(Binary-observable: a host with one in-flight slow verb receiving SIGTERM answers a new `echo.get` with `host_not_ready { kind: "draining" }`, returns the slow verb's result, and exits `0` within 10 s; with a verb that never completes it exits non-zero at 10 s with an `outcome = "error"` metric for that verb; a `SIGHUP` during the drain produces no `instance_check` record; a second SIGTERM exits non-zero within 1 s.)* [V-Reliability — graceful degradation with a bound; R-0121-a; Bolt M2]
- R-0118-m (database loss while serving): A pool acquire or driver error on a host-fn path SHALL surface to the caller as the distinct JSON-RPC error `storage_unavailable` (custom code; API Contract error table), never as a generic internal error and never as `host_not_ready` (the host *was* ready when the call was accepted); pool acquire is bounded by an **acquire timeout** code constant of `5 s`. An observed pool or driver error SHALL trigger an immediate out-of-cycle instance check with `trigger: "error"`, rate-limited to one such trigger per backoff floor (1 s) and coalesced per R-0118-a; if the check finds R-0117-i unmet, readiness goes false and subsequent calls get `host_not_ready`. A write cut by a connection loss after the host sent `COMMIT` but before the reply arrived is **unacknowledged** to the caller (`storage_unavailable`), and R-0121-a makes no claim about it. *(Binary-observable: killing the instance while a verb's query is in flight yields `storage_unavailable` to that caller within 5 s, an `instance_check { trigger: "error" }` record, and `503 /ready` with `R-0117-i unreachable`; a verb issued after that gets `host_not_ready`; the mid-write kill scenario under R-0121.)* [V-Reliability — a dependency failure mid-call is designed, not discovered; R-0010-f — error classes are distinguishable; Bolt M3]

### R-0119 — Connection configuration and the credential at rest (Amended 2026-10-19, #4018; anchors [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) §Amendment 2026-10-19; replaces R-0116-e's no-stored-secret design for an instance the host does not own)

*R-0116-e dissolved the credential question by owning the cluster and reaching it over a peer-authenticated socket. The operator's instance may be remote, so a credential can exist; this requirement bounds where it lives and keeps the no-secret shape available where it still fits. ⚠ The Postgres client library the host uses parses far more than it inspects (Warden, MEASURED in sqlx-postgres 0.9.0 `options/parse.rs:69-111`): `?password=`, `?host=` / `?hostaddr=` overrides, `options=…`, multi-host lists, `PG*` environment defaults, an always-run `~/.pgpass` lookup, and unknown query keys logged **with their values**. A URL denylist cannot close that; the host therefore never hands the URL to the driver. Keystone anchors: **V-DataMinimization** — a credential that need not exist is not held, so peer authentication over a socket stays the recommended local shape; **V-Security** — a secret never travels in the environment, the command line or a log, and the connection options are built from an allowlist; **P-SecurityLayered** — the control enumerates the permitted, and a control that errors denies; **V-Consistency** — the file-under-the-host-uid shape is the one R-0008-e and R-0014-d already use.*

- R-0119-a (connection options are built explicitly from an allowlist; the driver never sees the URL or the environment): The host SHALL read `MNEMRA_DATABASE_URL`, parse it itself, and construct the driver's connection options **field by field** (`PgConnectOptions` or its successor: user, one host **or** one socket directory, port, database, `sslmode`, `sslrootcert`, `application_name = "mnemra-host"`, the password from R-0119-b when and only when R-0119-d permits one); it SHALL NOT call the driver's URL parser and SHALL NOT let the driver read any `PG*` environment variable. The URL grammar the host accepts is a **closed allowlist**: scheme `postgres` or `postgresql`; userinfo with a user and **no password**; exactly one host component — a literal IPv4/IPv6 address, a hostname, or empty with `host=/absolute/socket/dir` in the query; an optional port; a database path; and query keys from exactly `{ host, port, sslmode, sslrootcert }`. Any other query key (`password`, `hostaddr`, `options`, `sslkey`, `sslcert`, `passfile`, unknown keys), a multi-host list, a `hostaddr`, or a password in userinfo SHALL be refused with `config_rejected { reason }` naming the offending key, before any connection is attempted and **without logging the offending value**. At process start the host SHALL scrub every `PG*` variable (`PGPASSWORD`, `PGPASSFILE`, `PGHOST`, `PGHOSTADDR`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE`, `PGSSLROOTCERT`, `PGOPTIONS`, `PGSERVICE`, `PGSERVICEFILE` and the rest of the libpq set) from its own environment, so neither the driver nor a child process inherits one — and because `std::env::remove_var` is `unsafe` under edition 2024 (the workspace's edition; it races any concurrent reader of the environment), the scrub SHALL run in `main` **before the async runtime or any other thread starts**, as the first statement after argument parsing, with a source check asserting that ordering. Local-versus-remote (R-0117-f, R-0119-d) SHALL be classified from the **parsed** options — socket directory present, or host is a literal loopback address — never from the URL text. An unset or empty `MNEMRA_DATABASE_URL` yields `connection_not_configured`. All of these are hard, non-exiting refusals (R-0118-b). The host SHALL log the connection as user, host-or-socket, port and database only (R-0004-h). *Rejected: a password inside the URL or a `MNEMRA_DATABASE_PASSWORD` variable — the process environment is readable by every same-uid process and appears in crash dumps and diagnostics; a denylist of URL keys — the driver's grammar is wider than any list the host maintains, and an omission fails open.* *(Binary-observable — **one seeded test per bypass**: `postgres://u:secret@h/d` → `config_rejected { reason: "password_in_url" }` and `secret` in no record; `postgres://u@h/d?password=secret` → `reason: "query_key_forbidden", key: "password"` and `secret` in no record; `?hostaddr=10.0.0.9` → `key: "hostaddr"`; `?options=-c%20…` → `key: "options"`; `postgres://u@h1,h2/d` → `reason: "multi_host"`; `?frobnicate=1` → `key: "frobnicate"`; with `PGPASSWORD=secret` and `PGHOST=evil` in the spawn environment the host's own `/proc/self/environ` (Linux) carries neither after start and the connection goes to the configured host; with a seeded `~/.pgpass` line matching the configured host and user, a peer-auth socket connection sends no password (R-0119-e); the options object handed to the driver has `application_name = "mnemra-host"`.)* [P-SecurityLayered — enumerate the permitted; P-GuaranteeByMechanism; V-Security; Warden H1]
- R-0119-b (the password file — read safely, re-checked on every read, stay-up on failure): When R-0119-d permits a password, the host SHALL read it from the file named by `MNEMRA_DATABASE_PASSWORD_FILE` (default `~/.config/mnemra/db-password`, beside the admin token file, R-0008-e). **Every read** — at boot, on `SIGHUP`, and by `mnemra check-db` — SHALL open the path with `O_NOFOLLOW` (a symlink is refused), `fstat` the **opened descriptor** (never a path-based `stat`, so there is no check-then-open window), and require: a regular file; no group or world **write** bit and no world **read** bit; and owner = host uid with no group read bit (the bare-host shape, `0600`) — **or**, only when the operator has set `MNEMRA_CREDENTIAL_MOUNT=1` **and** the process observes container evidence — any of `/.dockerenv`, `/run/.containerenv`, a `/proc/1/cgroup` line naming a container runtime, or an orchestrator environment marker (`KUBERNETES_SERVICE_HOST`, or `container` as set by podman and systemd-nspawn); the orchestrator marker is needed because under cgroup v2 with containerd or Kubernetes `/proc/1/cgroup` is typically `0::/` and neither marker file exists, so file evidence alone would refuse the primary mounted-Secret shape — *all of these markers INFERRED from general knowledge, not measured; the integration test under the CI container is the measurement* — owner = root with the file readable through a group the host belongs to (the Kubernetes Secret-mount shape: root-owned, `fsGroup`-grouped, `defaultMode: 0440`). The relaxation is opt-in and evidence-gated so a bare host never silently accepts a root-owned group-readable secret; the container section of the deployment document sets the variable, a root-owned file without the variable reports `credential_file_rejected { reason: "owner" }` whose guidance names the variable, and the variable without container evidence reports `reason: "not_a_container"`. *Residual, labelled: the evidence is a marker file, a cgroup string or an environment variable, any of which a root-level writer on a bare host could plant; the gate is against misconfiguration, not against a root-level adversary, and the deployment document says so. The Kubernetes shape itself is **latent at V0**: a stdio host has no transport to serve under an orchestrator (R-0118-k), so the orchestrator marker becomes load-bearing only with the HTTPS shared-service transport amendment (#4127), and it is written now so that amendment does not re-open this clause.* A failed check SHALL NOT exit: it reports `credential_file_rejected { path, reason, guidance }` as a hard not-ready reason (maintainer ruling 2026-10-19, activity 7762), **drops any previously loaded secret** from memory so a later successful read cannot be shadowed by a stale one, and the `guidance` names `chmod 0600` for a file the operator owns and `defaultMode: 0400`/`0440` plus `fsGroup` for a mounted Secret. The file's trailing newline, if any, is stripped. The host SHALL re-read the file on every forced retry (R-0118-d), so the operator's rotation procedure is: set the new password on the instance (`\password`, R-0118-d), write the file, `SIGHUP` the host; the pool is rebuilt and new connections use the new value. No automatic rotation exists; rotation is the operator's and this is its reload path. **The password-file shape is the primary shape for containers** (a mounted Secret), while peer authentication over a socket (R-0119-c) is the primary shape for a bare host; the deployment document SHALL present each first in its own section. - R-0119-c (peer authentication, no secret, server-side identity checked first): When the options name a unix socket directory, the host SHALL use peer authentication and no password (a password file is not read), and before sending the first byte on the socket SHALL perform the R-0117-f(ii) peer-uid and socket-directory check; this is the **recommended** shape for a bare-host local instance and the operator document SHALL present it first in the bare-host section. The ident map is the operator's (R-0117-j item 5). *(Binary-observable: with `postgres://mnemra@/mnemra?host=/var/run/postgresql`, `MNEMRA_DATABASE_PASSWORD_FILE` unset and no default file present, the check reports `R-0117-i met` and the host serves; a socket pre-created by a test in a directory owned by another uid is refused with `transport_unauthenticated` and zero bytes written.)* [V-DataMinimization — a credential that need not exist is not held; V-Simplicity; maintainer ruling 7771 — local spoofing is mitigated, not accepted]
- R-0119-d (the transport floor is enforced on the parsed options): From the parsed options the host SHALL classify the connection as **socket** (socket directory present) or **TCP** (any host, loopback included). TCP SHALL require `sslmode = verify-full` and a `sslrootcert`; any weaker or absent `sslmode` is refused with `config_rejected { reason: "sslmode_below_floor" }` before connecting. A password (R-0119-b) is permitted **only** on a TCP connection that satisfies that floor; a socket connection with a password file configured is refused with `config_rejected { reason: "password_over_socket" }`, and a TCP connection without a password file is refused with `connection_not_configured { missing: "password_file" }` (because `trust` is banned by R-0117-j item 6 and `peer` does not exist on TCP). *(Binary-observable: `postgres://u@127.0.0.1/m` with a password file → `sslmode_below_floor`; `…?sslmode=require` → the same; `…?sslmode=verify-full` without `sslrootcert` → `config_rejected { reason: "sslrootcert_missing" }`; `…?sslmode=verify-full&sslrootcert=/p` with a password file → connects; `postgres://u@/m?host=/run/pg` with a password file configured → `password_over_socket`.)* [P-SecurityLayered — the floor is a configuration-time control ahead of the runtime check; R-0117-f; Warden H2]
- R-0119-e (`.pgpass` is closed by mechanism): The driver's `~/.pgpass` / `PGPASSFILE` lookup runs on every connect where no password was set (Warden, MEASURED: `apply_pgpass()` always runs in sqlx-postgres 0.9.0). The host SHALL make that lookup inert — by the mechanism the implementation chooses (an explicit empty-password sentinel the driver treats as set, pointing the lookup at a path that cannot exist, or a driver option if one lands) — such that **no password reaches the wire except the one R-0119-b supplied**. *(Binary-observable: with a seeded `~/.pgpass` whose line matches the configured socket, user and database, and no password file configured, the peer-auth connection sends no password message (driver trace or a fake-server harness) and succeeds; with the same `~/.pgpass` and a TCP configuration whose password file is wrong, R-0117-i reports `auth_failed` rather than succeeding on the `.pgpass` value.)* [P-GuaranteeByMechanism — the second path is closed by a test, not a sentence; V-Honesty — the earlier "SHALL NOT depend on it" is replaced by a measured fact and a mechanism]
- R-0119-f (pool size, connection lifetime and the connection arithmetic): The serving pool's maximum size SHALL be the operator-configurable `MNEMRA_DB_POOL_SIZE` (default `8`, range `1..=64`, a value outside the range refused with `config_rejected`), with the acquire timeout of R-0118-m and a **maximum connection lifetime** code constant of `5 min` (R-0117-d). The host's connection budget on the instance is: steady state pool size + 1 (the instance check's **dedicated** connection, R-0118-a); during a pool rebuild (R-0117-d) transiently up to 2 × pool size + 1; and + 1 while `mnemra init` runs under the owner role. R-0117-j item 4 states the `max_connections` arithmetic the operator sizes against with the 2× factor. *(Binary-observable: with `MNEMRA_DB_POOL_SIZE=3` and three verbs held in flight, a fourth verb's acquire waits and fails with `storage_unavailable` after 5 s; `pg_stat_activity` for the serving role never exceeds 4 rows in steady state and never exceeds 7 during a `SIGHUP` rebuild; a pooled connection's `backend_start` is never older than 5 min plus one acquire; `MNEMRA_DB_POOL_SIZE=0` and `=65` are refused.)* [V-Reliability — bounded resources; V-Observability — the budget is a stated number the operator can size to]
- R-0119-g (the owner credential — held only by `mnemra init`): `mnemra init` SHALL connect as the owner role using `MNEMRA_DATABASE_OWNER_URL` (same grammar and allowlist as R-0119-a) and `MNEMRA_DATABASE_OWNER_PASSWORD_FILE` (same rules as R-0119-b) or peer authentication; the serving host SHALL NOT read either variable and SHALL NOT hold the owner credential at any time. **The owner credential SHALL be absent at serve time**: a serving process started with `MNEMRA_DATABASE_OWNER_URL` or `MNEMRA_DATABASE_OWNER_PASSWORD_FILE` set, or with the default owner password-file path present and readable by the host uid, reports the hard not-ready reason `owner_credential_present { guidance }` and does not serve — the serving uid can read any file it can read, and the two-role split stops SQL injection but not a compromised host process, so the owner secret must not be reachable from the serving process's uid at all (supplied to `mnemra init` only, on the operator's session, and removed or made unreadable afterwards; the ident map must not map the serving uid to the owner role, R-0117-j item 5). **The limit of this check, named:** `owner_credential_present` sees exactly the two variables and the default owner password-file path; a copy of the owner secret anywhere else the serving uid can read is invisible to it, so "the owner credential is unreachable from the serving uid at all" stays an **obligation** (R-0117-j item 5), not a verified clause. The two credentials may name the same instance and database; they SHALL name different roles, and `mnemra init` SHALL refuse (`config_rejected { reason: "owner_equals_serving" }`) when the owner URL's user equals the serving URL's user. *(Binary-observable: `mnemra init` with the serving role's URL in `MNEMRA_DATABASE_OWNER_URL` is refused; the serving host spawned with `MNEMRA_DATABASE_OWNER_URL` set reports `503 /ready` with `owner_credential_present`; spawned with the default owner password file present at mode `0600` under the host uid it reports the same; no serving-path code reads either variable (a source check); after `init`, the serving role's `pg_class.relowner` and `nspowner` scans (R-0117-c) report `met`.)* [P-LeastAuthority — the authority to change the schema is never standing in the serving process; maintainer ruling 7771]

### R-0120 — Test substrate: how test fixtures obtain a Postgres, locally and in CI, with no embedded engine (Amended 2026-10-19, #4018; anchors [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) §Amendment 2026-10-19, R-0018-b, the CI tier-2 spec `docs/specs/2026-07-02-ci-flake-tier2-shared-engine.md` R-0026 / R-0027 / R-0032 / R-0033)

*R-0018-b stands: integration tests run against a real Postgres with the real extension, never a mock. The tier-2 spec's fixture shape — one acquisition entry point, one boot per binary, a fresh uniquely named database per test, an application-role pool and a named privileged provisioning path, a guard lint and a membership enumerator — transfers almost unchanged; what changes is where the engine comes from. ⚠ That spec is `approved` and names `EmbeddedEngine::start` / `postgresql_embedded` as its guarded symbols (R-0032) and "boots the binary's engine" (R-0026); this amendment falsifies those words, which is raised for that spec's own amendment (P-0010 §Amendment, "Records this amendment falsifies"), not edited here. Keystone anchors: **P-TrustworthySignal** — a missing substrate fails the test loudly and never skips; **P-TestableByDesign** — the fixture takes its server as an injected input; **V-Consistency** — one mechanism for local, CI and smoke.*

- R-0120-a (two inputs, three roles, never a skip): The shared fixture entry point SHALL obtain its server from exactly two environment variables. `MNEMRA_TEST_DATABASE_URL` names the **harness role**: `LOGIN CREATEDB CREATEROLE`, not a superuser, no `BYPASSRLS`; it provisions per-test databases and, per run, creates a **run-scoped owner role** and a **run-scoped serving role** (`mnemra_test_<run>_owner`, `mnemra_test_<run>_serving`, with the R-0117-c attribute set) — so the role the host-under-test connects as is never the harness role, which holds `CREATEDB` and would fail R-0117-c (Charon C7); the harness role's `CREATEROLE` is what lets the drift scenarios run `ALTER ROLE <serving> SET …` and `RESET`. `MNEMRA_TEST_SUPERUSER_URL` names a superuser on the same server and SHALL be read by **one gated test binary only** (`tests/instance_check_privileged.rs`, the R-0117 negative cases that need a superuser connection or a `BYPASSRLS` grant); a source check SHALL fail when any other test file reads it. Both variables SHALL be required: an absent or unreachable variable fails the first acquiring test with a message naming the variable and the one-line remedy from the deployment document; the fixture SHALL NOT skip, SHALL NOT fall back to a default URL, and SHALL NOT start a server. **Before any provisioning the fixture SHALL refuse a server that holds a non-test mnemra database, failing closed**: for every database in `pg_database` other than `template0`, `template1` and `postgres`, and other than `mnemra_test_*` names, the fixture connects and looks for the mnemra migrations table — a database it **cannot connect to** (no `CONNECT` privilege, `datallowconn = false`) is treated as a possible production store and refused with `cannot verify <db>` (never skipped), a database carrying the table is refused with `refusing to run tests against a server holding <db>`; the marker is the migrations table, not the name, and there is no ignore list. **`<run>` is defined as the whole gate invocation**: the value of `MNEMRA_TEST_RUN_ID`, which the `just ci` recipe exports once as `<hosthash>_<pid>_<pid-start-epoch>` of the `just` process (alive for the whole gate, so every one of the 42 test binaries shares one run id and one cache), and which a test binary started without the variable generates for itself from its own pid and start epoch (a standalone run is its own invocation); the fixture SHALL refuse a value that does not parse to the three fields. `<hosthash>` is the first 8 hex characters of a hash over the hostname, the machine boot id and the container id when one is present (`/proc/self/cgroup` or `/proc/1/cpuset`) — so two containers that share a hostname get different hashes and one never sweeps the other's live run, whose pids it cannot see (`kill(pid, 0)` does not cross a pid namespace; stated limit). Postgres truncates identifiers to **63 bytes silently**, so every generated name SHALL be built to fit (`mnemra_test_` 12 + hash 8 + pid ≤ 7 + epoch 10 + 3 separators = 40, leaving 23 for `<binary>_<n>`, with `<binary>` truncated to fit) and **parsed from the right** (`<n>`, `<binary>`, epoch, pid, hash are fixed-width or delimiter-terminated from the right, so a truncated binary name cannot shift the fields). At fixture start the sweep SHALL remove: (a) every database and role under the fixture's **own** run prefix (a restart of the same pid-and-epoch is impossible by construction), and (b) every `mnemra_test_<hosthash>_<pid>_<epoch>_*` database and role whose `<hosthash>` equals this process's and whose `<pid>` is **dead** (`kill(pid, 0)` → `ESRCH`) or whose live process's start epoch differs from `<epoch>` — the SIGKILLed run that never reached teardown. It SHALL NOT touch another `<hosthash>`'s prefix or a live same-hash run (two lanes may share one server, and a global sweep is the cross-lane reap trap in a new form). **Cost of the fail-closed production-store scan, stated:** one `pg_database` read plus one connect attempt per non-test database, which at 42 Postgres test binaries per `just ci` would run 42 times; the fixture therefore **caches the scan result per run** in a file under the OS temporary directory named by `<run>` (the gate-level id above, so the 42 binaries of one `just ci` share it), and the scan runs once per gate invocation while each later binary reads the cache; a standalone binary run has its own id and scans once. **Reboot sweep (age threshold):** because `<hosthash>` includes the boot id — kept, since it is what separates two containers that share a hostname and show no container id (cgroup v2 `0::/`) — the pre-reboot orphans of a SIGKILLed run on a persistent machine would never match a post-reboot hash; - R-0120-b (per-test database from a template): Each test SHALL receive a fresh database named `mnemra_test_<run>_<binary>_<n>` created `TEMPLATE mnemra_test_template`, where the template is a database the operator or CI setup created once, as a superuser, with `CREATE EXTENSION vector` applied — so no test needs the privilege to install the extension and R-0117-b is exercised for real (the tier-2 R-0027 "per-database `CREATE EXTENSION vector`" clause becomes "inherited from the template"). - R-0120-c (CI): The CI workflow SHALL provide the server as a GitHub Actions service container running the pgvector project's official PostgreSQL 16 image, **pinned by image digest** in the workflow, with a `pg_isready` wait before any step uses it, and a setup step that creates the harness role, the template database and the extension from the service's superuser and exports both URLs to the job. **The digest pin needs a firing bump mechanism because Dependabot is disabled on this repository** (`CLAUDE.md`): a scheduled weekly workflow SHALL resolve the image tag's current digest and fail when it differs from the pinned one, naming both — the failure is the trigger to review and bump. ### R-0121 — Durability across host restart against the operator's instance: the invariant, what the host verifies, and the restart acceptance (Amended 2026-10-19, #4018; anchors the brief's Success criterion "Durable across restart", [P-0010](../src/adrs/P-0010-storage-substrate-engine.md) §Amendment 2026-10-19, the [overview](../src/architecture/overview.md) Reliability / durability axis; supersedes R-0116-a and R-0116-h)

*The maintainer's 2026-10-18 correction (activity 7472, verbatim: "data surviving restarts was our problem, if an embedded postgres didn't use a data directory that would be have been a non-starter for such a thing") fixes the framing: the persistence defect (#3565) was mnemra's own `.temporary(true)` (MEASURED `libs/mnemra-host/storage/postgres/engine.rs:617` at `57cfeca`), not a property of embedding. Its fix under this amendment is a **correction** — the host no longer owns any data directory, temporary or otherwise — and is never a benefit of the move. The durability requirement itself stays in the core: the invariant below, and R-0117-d / R-0117-j for the half that is now the instance's. Keystone anchors: **V-Reliability**; **P-CheckCoversTheClaim** — the host claims exactly what its acceptance restarts and its check verifies, and names what it relies on Postgres for.*

- R-0121-a (the invariant): Every write acknowledged to a caller — an `artifact.create` / `artifact.update` / `artifact.delete` host-fn, or the MCP verb wrapping it, that returned success — before the host stops SHALL be reflected identically after the host next starts against the same instance and database, for a clean stop (SIGTERM, graceful drain; stdin EOF counts as a clean stop, resolving the R-0116 plan's SG-15) and for a hard kill of the host process (SIGKILL). "Reflected identically" is R-0116-a's definition, carried: `frontmatter` semantically equal as parsed JSON, `body` byte-equal, each acknowledged delete absent, per-table row count under the workspace unchanged; an unacknowledged in-flight write MAY be present or absent. A write that cannot be durably committed SHALL NOT be acknowledged: the dispatch surfaces the failure as R-0004-a `outcome = "error"`. *(Binary-observable: the two restart scenarios below.)* [brief Success criteria "Durable across restart"; V-Reliability]
- R-0121-b (what the host relies on Postgres for, named): Survival of an acknowledged write across a crash or restart of the **instance** itself is PostgreSQL's WAL guarantee under the settings R-0117-d verifies and the storage placement R-0117-j names; the host neither tests nor re-implements it. The host's contribution to that guarantee is the check: a drift in any R-0117-d setting takes readiness false within one interval, so the host never acknowledges a write under weakened durability for longer than that interval. The embedded design's "hard kill of the storage engine" scenario is therefore **dropped from the host's acceptance with reason**, not parked: the host cannot kill a process it does not own, and a claim about Postgres's crash recovery is Postgres's to make. *(Binary-observable: the R-0117-d drift scenario; the deployment document states this reliance in the operator obligations section.)* [P-CheckCoversTheClaim; V-Honesty — the reliance is named, not implied]
- R-0121-c (restart acceptance placement): The restart acceptance SHALL be out-of-process in the `verify-smoke` gate (`libs/mnemra-host/tests/smoke_e2e.rs`): spawn the production binary with `MNEMRA_DATABASE_URL` pointing at a fixture-provisioned database as the run-scoped serving role (R-0120-e), write through MCP stdio, stop the child by the scenario's method, spawn it again against the same URL, read back over MCP. It constructs no engine and no server in test code. The harness reads SQL observables (`SHOW` values, row counts) over `MNEMRA_TEST_DATABASE_URL` against the same database. *(Binary-observable: the scenarios pass under `just verify-smoke`; the harness's SQL session and the child's connection resolve to the same `current_database()`.)* [P-TestableByDesign; tier-2 R-0033 partition unchanged]
- R-0121-d (mid-write loss of the instance): With a verb's write in flight, loss of the instance connection SHALL leave the write **unacknowledged** (`storage_unavailable`, R-0118-m), and after the instance returns the host SHALL serve again without a restart; the write is either wholly present or wholly absent (Postgres transaction atomicity), never partial. The harness cannot kill the operator's instance in CI, so this scenario SHALL use the **fake-server or connection-cut seam** (a `test-hooks` injection that closes the pool's connections mid-query), with the real-instance half covered by R-0117-d's settings check and R-0121-b's named reliance. *(Binary-observable: the mid-write kill scenario below.)* [V-Reliability; P-CheckCoversTheClaim — the claim is scoped to what the seam can exercise; Bolt M3]

## Scenarios

### Scenario: Single-node V0 substrate initialization — happy path

**Given** a fresh Postgres instance with no mnemra-core schema, and the mnemra-core binary built with signed `core: true` plugin artifacts and embedded verification material  
**When** the operator runs `mnemra init`  
**Then** the system creates all substrate tables and indexes, installs the bundled `pgvector` extension against the embedded engine (no `timescaledb` — re-derived 2026-06-09 per [observability baseline](../src/architecture/overview.md#observability); no in-app observability hypertable, retention policy, or continuous aggregate is created), creates the `default` workspace, initializes all seven builtin components, initializes the plugin pool (3–5 instances per `core: true` plugin type), verifies plugin signatures synchronously before creating any instance, emits a structured health event to the OTel/stdout surface, and responds to a `GET /health` request on the loopback-only listener with the structured detail body `{ "postgres": true, "pgvector": true, "workspace_default": true, "overall": "ok" }` (loopback IS the gate at V0 — no admin token is required on the detail body; the listener binds `127.0.0.1` only, so every caller it serves is on loopback).

### Scenario: Plugin signing chain operates on load — happy path

**Given** a `tasks` plugin manifest at `tasks/manifest.toml` declaring `schema_version = 1`, `core = true`, the valid `[signature]` section signed by the mnemra root key on the build host  
**When** the host loads the `tasks` plugin at startup  
**Then** `verify()` is called synchronously and returns `Ok`; a per-instance host-fn allowlist is compiled from the manifest's `[host_fns]` section; a pool of 3–5 `tasks` plugin instances is created; each instance is ready to service `task.*` MCP verbs.

### Scenario: MCP verb dispatches under `WorkspaceCtx` — happy path

**Given** an MCP client connected over stdio presenting a valid admin token associated with `workspace_id = W1`  
**When** the client sends a JSON-RPC request for verb `task.create` with valid arguments  
**Then** `P-builtin-auth` validates the token; a `WorkspaceCtx { workspace_id: W1, role: Admin, token_id: T1 }` is constructed at a single construction site; the `WorkspaceCtx` is passed as the first parameter to the `artifact.create` host-fn; the host derives `workspace_id` from the context and performs `INSERT INTO tasks (...) WHERE workspace_id = W1`; the response carries the new artifact's ULID; a per-verb metric record is emitted to the OTel/stdout surface for verb `"task.create"`, outcome `"ok"`, and measured `duration_ms` (not written to an in-app hypertable — re-derived per [observability baseline](../src/architecture/overview.md#observability)).

### Scenario: MCP verb dispatches to a typed content export — happy path

**Given** a `tasks` plugin built as a component that exports the typed `content` interface (`create`/`get`/`list`/`update`/`delete`) and exports no `run`-shaped string-dispatch function, with `task.create` declared in its manifest `verbs` list, and an MCP client connected over stdio presenting a valid admin token for `workspace_id = W1`  
**When** the client sends a JSON-RPC request for verb `task.create` with valid arguments  
**Then** after `DF-auth-check` and the per-verb capability check against the manifest `verbs` list (R-0010-d), the host invokes the **typed `content.create` export** on a pooled `tasks` instance — resolved statically against the fixed `content` interface, with no runtime export-registry lookup (R-0019-a, R-0019-c) — passing the typed arguments across the WIT boundary and receiving a typed return; no string-based verb-dispatch path is traversed (R-0019-b); the response carries the new artifact's ULID. *(Companion: a manifest-declared verb with no matching typed export returns the R-0019-d structured non-dispatchable error and leaves the pre-dispatch permission outcome unchanged — covered by R-0019-e, not a separate scenario at V0 since no such verb ships.)*

### Scenario: Observability emits during a dogfood session — happy path

*(Re-derived 2026-06-09 per [observability baseline](../src/architecture/overview.md#observability): observability is emitted, not stored in-app. No metrics/events hypertable or continuous aggregate exists; the percentile distribution is derivable from the emitted `duration_ms` values at the operator-chosen sink.)*

**Given** the substrate is initialized (no in-app observability store; the server emits to stdout/OTel)  
**When** a typical dogfood session generates 50 MCP verb calls across `task.create`, `task.update`, `task.list`, `task.get` over 1 hour, with no persistent observability backend configured  
**Then** 50 per-verb metric records are observable on the OTel/stdout emission surface, each carrying `workspace_id`, `verb`, `outcome`, `duration_ms`; `p50`/`p95`/`p99` per `(verb, workspace_id, outcome)` are derivable from the emitted `duration_ms` values for the window; `\d+` introspection shows **no** metrics/events hypertable and `\dx` does **not** list `timescaledb`; emission succeeds with no observability database present (storage-independent emission, R-0004-c/f).

### Scenario: Admin token authenticates a destructive operation — happy path

**Given** the admin token file at mode 600 with `token_value = T_ADMIN`, and a `admin_tokens` row `{ token_hash: BLAKE3(T_ADMIN), workspace_id: W1, scopes: ["admin"] }`  
**When** the operator runs `mnemra workspace list --token T_ADMIN`  
**Then** the CLI performs a hash lookup `BLAKE3(T_ADMIN)` against `admin_tokens.token_hash`; the lookup returns the row; `WorkspaceCtx { workspace_id: W1, role: Admin, token_id: <row id> }` is constructed; `workspace list` executes and returns the list of workspaces scoped to `W1`.

### Scenario: Signing verification failure — plugin SHALL NOT load

**Given** a plugin artifact whose `[signature]` section contains bytes that do not verify against the embedded mnemra root key  
**When** the host attempts to load this plugin at startup  
**Then** `verify()` returns `Err`; the plugin load is rejected with a structured error naming the plugin's `name` and `version`; no plugin instance is created; the host continues startup (it does not crash); the MCP server does not expose any verbs for the rejected plugin; the error is emitted as a structured event (destination per R-0004).

### Scenario: Resource limit breach — kill-and-replace

**Given** a `tasks` plugin instance running verb `task.list` that enters an infinite loop (pathological implementation)  
**When** the epoch-interruption deadline (5 seconds) fires  
**Then** the Wasmtime `Store` traps with an epoch deadline error; the host catches the trap; a structured event is emitted (destination per R-0004): `{ event_type: "plugin_limit_violation", payload: { workspace_id: W1, plugin_id: "tasks", plugin_version: "0.2.0", limit_type: "epoch_deadline", limit_value: 500 } }`; the pool slot is poisoned; a new `tasks` instance is created for the pool; the caller receives a structured error `{ code: "plugin_execution_timeout", plugin: "tasks", verb: "task.list" }`; the host process does NOT panic.

### Scenario: Admin token mismatch — 401

**Given** an MCP client presenting a token string `T_BOGUS` for which no matching row exists in `admin_tokens`  
**When** the client sends a JSON-RPC request for any verb  
**Then** `P-builtin-auth` performs `SELECT ... WHERE token_hash = BLAKE3(T_BOGUS)`; the query returns zero rows; the MCP handler returns JSON-RPC error code distinguishable as authentication failure (NOT verb-not-found, NOT parameter-invalid); no `WorkspaceCtx` is constructed; no host-fn is invoked; no workspace data is accessed.

### Scenario: Cross-workspace SQL leak — compile-time ABI prevention (build-time test)

**Given** a `core: true` plugin author who attempts to declare a host-fn that accepts `workspace_id: Uuid` as a write-path parameter  
**When** the author compiles the plugin against the WIT-defined host-fn interface  
**Then** the WIT-generated bindings do not include any write-path function that accepts `workspace_id` as a parameter; the compiler rejects the attempt at the type boundary; no runtime check is necessary because the ABI makes the wrong thing impossible to express.

**Given** an admin token row with `scopes = ["read_observer"]` associated with `workspace_id W1`

### Scenario: Artifact-list keyset pagination walks a type end-to-end — happy path

**Given** a workspace `W1` holding `N` artifacts of type `task` (with `N` greater than one page), and an MCP client connected over stdio presenting a valid admin token for `W1`  
**When** the client walks the type starting from `cursor = none`, following `next-cursor` on each call until `has-more = false` — through the full path client → guest `content.list` export → host-fn `artifact.list` → Postgres  
**Then** a finite sequence of `artifact-page` records is returned in `id`-ascending (creation) order such that: on **every** page `has-more = true` **iff** `next-cursor = some` (R-0020-b); on **every non-final page** `next-cursor = some(ids.last())` — the resume cursor equals the `id` of the last row on the page (R-0020-b); on the **final** page `has-more = false` **and** `next-cursor = none`; the concatenation of all pages' `ids` contains each of the `N` artifacts **exactly once** (no duplicates, no gaps); global order is `id`-ascending across page boundaries; the walk **terminates** (no infinite cursor loop); and the walk is exercised **through the guest `content.list` export**, not only the host-fn (the end-to-end path is the asserted surface). [Frame QA-1]

### Scenario: Artifact-list pagination DoS bounds — size cap and scan-cost timeout

**Given** the keyset read path with the host-side clamp (R-0020-c) and host-side `statement_timeout` (R-0020-d) active  
**When (A — size)** a caller requests `limit = 100_000` against a type holding more than 500 artifacts  
**Then (A)** a single bounded `artifact-page` is returned with `ids.len() <= 500` (clamp) even though the requested `limit` exceeded the cap; rows **returned** are `<= cap + 1` (fetch-one-extra; no `COUNT`); and no list path issues an unbounded (`LIMIT`-less) query — closing the result-set-*size* half of the prior unbounded-`SELECT` finding.  
**And when (B — scan cost, adversarial)** a caller issues a `filters` predicate on a **non-indexed** frontmatter field (outside the four R-0001-d expression-indexed fields) matching sparsely or zero rows, against a type holding more than `cap` artifacts — forcing `ORDER BY id LIMIT cap+1` to walk the entire `id`-btree tail  
**Then (B)** the query is **canceled by the `statement_timeout`** within the bounded budget and surfaces as a structured error — observable as the **R-0004-a metric `outcome = "timeout"`** (not `"ok"`) with a bounded wall-clock `duration_ms` — rather than completing an unbounded full-tail scan, closing the *scan-cost* half the cap leaves open. [Frame QA-2]

**When** workspace `A` paginates the type across all pages, including under a cursor value that `B`'s rows would sort into  
**Then** only workspace-`A` artifacts are ever returned, on any page, for any cursor; the existing **R-0006-d / R-0018-d read-path CI lint stays green** across the rewrite (the `workspace_id` WHERE-clause condition is present on the new keyset read path — no new mechanism is introduced); and a **cross-workspace probe** returns **zero** `B`-owned `id`s on any page. [Frame QA-3]

### Scenario: Artifact-list cursor and `limit` boundary semantics

**Given** the `artifact.list` host-fn boundary validation (R-0020-e) ahead of query construction and the host-side clamp (R-0020-c/-f)  
**When** a caller supplies (a) a malformed `cursor` (not a 26-char ULID), (b) a well-formed but out-of-range `cursor` (valid ULID past the end), and (c) `limit = 0`  
**Then** each boundary input yields a bounded, defined outcome — never an unbounded query and never a leaked internal error: **(a)** the malformed `cursor` returns the **R-0010-f structured "parameter invalid" error** (not an empty page, not a raw Postgres error), and the error body contains **no DB/schema/Postgres internals** (R-0020-e no-leak posture); **(b)** the out-of-range valid-ULID `cursor` returns an **empty page** (`ids = []`, `has-more = false`, `next-cursor = none`), derivable from keyset `id > $cursor`; **(c)** `limit = 0` returns a **bounded** default-clamped page (`ids.len() <= 100`) and the emitted SQL is `LIMIT 101` — **never** a `LIMIT`-less or `LIMIT NULLIF`-zeroed query (R-0020-f), asserted against the actual emitted SQL. [Frame QA-5]

### Scenario: Artifact-list paging params excluded from telemetry

**Given** any paginated `artifact.list` / `content.list` dispatch carrying a `cursor` in and a `next-cursor` out, with the per-verb metric record (R-0004-a) and structured-log emission on the dispatch  
**When** the dispatch completes and emits its telemetry  
**Then** the emitted per-verb metric record contains `workspace_id` / `verb` / `outcome` / `duration_ms` and **does not** contain the `cursor` or `next-cursor` value (R-0004-a: no artifact IDs in the metric record), and the structured-log line for the dispatch likewise **omits** the `cursor` / `next-cursor` values — assertable by inspecting the emitted record/log (R-0020-g). [Frame QA-6]

### Scenario: Artifact-list empty type — zero artifacts

**Given** a workspace `W1` holding **zero** artifacts of type `task`  
**When** a client calls `artifact.list` for type `task` with `cursor = none`  
**Then** a single `artifact-page` is returned with `ids = []`, `has-more = false`, and `next-cursor = none` — the empty-set case satisfies the R-0020-b biconditional (`has-more = false` ∧ `next-cursor = none`); no error is raised and no `cap+1`-th probe row is implied. [R-0020-b]

### Scenario: Artifact-list exact-last-page boundary — final page exactly full

**Given** a workspace `W1` holding **exactly** `page_size × K` artifacts of type `task` (e.g., 200 at the default page size of 100), and a client walking from `cursor = none`  
**When** the client walks to the last page  
**Then** page 1 returns `ids.len() = 100` with `has-more = true` and `next-cursor = some(ids.last())`, and the 2nd (**final**) page returns `ids.len() = 100` with `has-more = false` and `next-cursor = none` — the final page is **exactly full** yet correctly reports end-of-set. This is the highest-value paging edge: it catches an `ids.len() == limit` end-of-set heuristic (which would wrongly report `has-more = true` on an exactly-full final page) in place of the R-0020-a **fetch-one-extra** mechanism. [R-0020-a, R-0020-b]

### Scenario: Artifact-list page-size cap boundary — limit 499 / 500 / 501

**Given** a workspace holding more than 501 artifacts of a type, and the host-side clamp `effective_limit = (limit == 0 ? 100 : min(limit, 500))` (R-0020-c)  
**When** a client requests `limit = 499`, then `limit = 500`, then `limit = 501`  
**Then** the effective page size is **499, 500, and 500** respectively (`min(limit, 500)`): `limit = 499` returns up to 499 ids; `limit = 500` returns up to 500 ids; `limit = 501` is **clamped** to 500 ids — every page returns `ids.len() <= 500`, and the emitted SQL `LIMIT` is `effective_limit + 1` (500 / 501 / 501) per fetch-one-extra. [R-0020-c]

### Scenario: Artifact-list foreign-but-valid cursor — zero foreign rows

**Given** workspaces `A` and `B` each holding artifacts of the same type, and a **well-formed 26-char ULID** cursor that is the `id` of one of `B`'s artifacts  
**When** workspace `A` calls `artifact.list` passing `B`'s artifact `id` as `cursor`  
**Then** the keyset `id > $cursor` predicate is ANDed with `workspace_id = ctx.workspace_id` (R-0006-d), so the returned page contains only `A`-owned ids whose `id` sorts after the cursor value — **never** any `B`-owned row; the foreign-but-valid cursor is safe (it can at most return an empty or shifted page **within `A`'s own workspace**), and the cross-workspace probe returns **zero** `B`-owned ids on any page. [R-0020-e]

### Scenario: Artifact-list concurrent insert during walk — forward-non-losing keyset

**Given** a client mid-walk of type `task` under `cursor = C`, having already emitted all ids `<= C`  
**When** new artifacts of type `task` are inserted concurrently (each created after the cursor's row, so each sorts at `id > C` under the lexicographic = chronological `id` ordering)  
**Then** the newly-inserted `id > C` rows appear on a **later** page of the same walk (the walk is **forward-non-losing**: it neither loses already-emitted rows nor duplicates them); the walk is **not a point-in-time snapshot** — it MAY include rows created after the walk began, which is the **defined** keyset behavior, not a defect. [R-0020-a]

### Scenario: Artifact-list scan-cost statement_timeout — caller-visible query_scan_timeout

**Given** the keyset read path with the host-side `statement_timeout` (R-0020-d) armed **inside an explicit transaction**, exercised with a **test-only reduced `statement_timeout`** and a seeded row count large enough to exceed it under an adversarial sparse non-indexed `filters` predicate  
**When** the read-path query exceeds the `statement_timeout` and Postgres cancels it  
**Then** the dispatch surfaces **both** the R-0004-a metric `outcome = "timeout"` (not `"ok"`) with a bounded `duration_ms` **and** a caller-facing JSON-RPC **`query_scan_timeout`** error; the error body carries **no** Postgres/schema/DB internals (R-0020-e no-leak posture); and `query_scan_timeout` is **distinct** from `plugin_execution_timeout` (guest epoch) and `-32602` (parameter invalid). This scenario guards **both** the explicit-transaction requirement (a `SET LOCAL` outside a transaction would silently disarm the backstop and this cancellation would never fire) **and** the distinct-error-code requirement. [R-0020-d]

### Scenario: Artifact-list degraded DB connectivity mid-walk — structured error, resumable

**Given** a client mid-walk of a type, having received `next-cursor = C` on the prior page  
**When** DB connectivity degrades (connection refused / dropped) on the next `artifact.list` call  
**Then** the dispatch returns a **structured error** (not a crash, panic, or hang) — the host process does not panic; once connectivity recovers, the client retries the **same call with `cursor = C`** and the walk **resumes from exactly where it left off** (keyset cursors are stateless and idempotent — there is no server-side walk state to lose). [R-0020-a]

### Scenario: Artifact-list concurrent cursor churn under pool pressure

**Given** multiple clients concurrently walking the same and different types, with the fixed 3–5-instance plugin pool (R-0016-a) under contention

**And given** a host whose password file is wrong, held for 120 s (the `auth_failed` backoff reaches 1, 2, 4, 8, 16, 32, 64 s)  
**When** `GET /ready` is read every 5 s throughout  
**Then** every response is `503` with `reasons[0].reason = "auth_failed"` and `next_retry_s` in the future, and none reports `stale_check` — the staleness bound tracks the current backoff (R-0118-f).  
**And given** a `test-hooks` injection that panics the check task once  
**Then** an `instance_check` record with every clause `unverifiable { error: "check_task_restarted" }` is emitted, readiness is `503` for one interval, and the following scheduled run reports `met`. [R-0118-a/-f]

### Scenario (Amended 2026-10-19): Instance lost mid-write — unacknowledged, distinct error, recovery without restart

**Given** a serving host and a `test-hooks` injection that closes every pooled connection while an `echo.create` is between its `INSERT` and its `COMMIT`  
**When** the injection fires  
**Then** the caller receives `storage_unavailable` (not `host_not_ready`, not a generic error) within 5 s, the row is absent (the transaction never committed), an `instance_check { trigger: "error" }` record follows within 1 s, and readiness goes `503` with `R-0117-i unreachable` if the probe also fails; when connections are restored the host serves again on the second consecutive `met` with its pid unchanged, and a re-issued `echo.create` succeeds exactly once. [R-0118-m, R-0121-d]

## API Contract

### Pagination return record (`artifact-page`)

*(Added 2026-06-29 per R-0020.)* The list direction returns a shared WIT record on both the host-fn import (`artifact.list`) and the guest export (`content.list`). It replaces the prior `list<string>` / `[{ id, frontmatter }]` list return — the return **narrows to ids-only** (no inline frontmatter; a caller resolves frontmatter via `artifact.get` per id, an accepted N+1 fan-out characterized on R-0020-b). The ids-only record is the shape locked by **intake Success criterion 1** (host-fn) and **Success criterion 2** (guest export); Frame D4 understated the import baseline (it modeled the prior return as `list<string>`, but the host-fn baseline was `[{ id, frontmatter }]` — so the import side genuinely drops inline frontmatter).

| Field | WIT type | Notes |
|-------|----------|-------|
| `ids` | `list<string>` | The page's artifact ULIDs, in `id`-ascending (creation) order |
| `has-more` | `bool` | `true` iff a further page exists; `true` **iff** `next-cursor = some` (R-0020-b invariant) |
| `next-cursor` | `option<string>` | When `some`: the `id` of the last returned row (the next call's `cursor`). `none` when `has-more = false` |

The paging input parameters added to both directions are `limit: u32` and `cursor: option<string>` (typed WIT params per R-0012-f / R-0019-b — not folded into `filters`). Host-side clamp: `effective_limit = (limit == 0 ? 100 : min(limit, 500))` (R-0020-c/-f).

### Health endpoint

**Path:** `/health`  
**Methods:** GET  
**Transport:** Dedicated loopback-only TCP listener; binds to `127.0.0.1` only; port configurable via `MNEMRA_HEALTH_PORT` env var (default: `8877`). This is NOT the MCP stdio transport.  
**Gate:** The loopback-only bind IS the gate at V0 — every caller that can reach the listener is on loopback, so the detail body is served to every caller the listener can serve; there is no admin-token gating at V0. *(Named tripwire: if the listener ever binds a non-loopback interface, admin-token gating on the detail body becomes required — unauthenticated callers then receive a status-code-only `200`/`503` and only admin-token callers receive the detail body.)*  
**Response (HTTP `200` healthy / `503` when a dependency is down):**

```json
{
  "postgres": true,
  "pgvector": true,
  "workspace_default": true,
  "overall": "ok"
}
```

`"overall"` values: `"ok"` (all deps reachable), `"degraded"` (partial), `"down"` (Postgres unreachable). *(Re-derived 2026-06-09 per [observability baseline](../src/architecture/overview.md#observability): the `timescaledb` field is removed — TimescaleDB is not a V0 substrate dependency (D8). The body reports the substrate dependencies the standalone binary owns. The health endpoint is the first API, started before config load — R-0004-g.)*

### Liveness and readiness endpoints (Amended 2026-10-19, #4018 — supersedes the single `/health` body above per R-0118)

**Transport:** the same dedicated loopback-only listener (`127.0.0.1`, `MNEMRA_HEALTH_PORT`, default `8877`), bound first; exactly two routes.

| Route | Question | `200` body | `503` body | Depends on the instance? |
|---|---|---|---|---|
| `GET /health` | Is the process alive and not wedged? | `{ "alive": true, "pid": int, "uptime_s": int }` | `{ "alive": false }` (runtime did not answer an in-process ping within 1 s) | **Never** (R-0118-e) |
| `GET /ready` | Can the host serve a call now? | `{ "ready": true, "last_run_at", "age_s", "checks": [ … ] }` | `{ "ready": false, "reasons": [ { clause, status, reason, detail?, guidance? } ], "next_retry_s": int, "last_run_at", "age_s", "checks": [ … ] }`; `reasons` carries `{ "reason": "starting" }` before `mark_ready`, `{ "reason": "stale_check" }` when the last completed check is older than 2 × the current scheduled interval + 10 s (70 s while serving; tracks the backoff while not ready), and `{ "reason": "draining" }` after SIGTERM | Yes — by design (R-0118-f) |

`checks` is the most recent completed `instance_check` result list (R-0118-a): one entry per R-0117 clause, `status ∈ { met, unmet, unverifiable, not_applicable }`. There is no `degraded` key at V0 (R-0118-i). Probe mapping (R-0118-g): liveness → `/health`; readiness → `/ready`; startup → `/health` or none; pre-flight and diagnostic → `mnemra check-db` (never a probe). The listener stays loopback-only, so an orchestrator uses exec probes at V0 (`mnemra health`, `mnemra ready`: client timeout 2 s; exit `0` on `200`, `1` on `503`, `2` when the listener refuses or times out; the orchestrator's probe timeout is set `≥ 3 s`). Metrics (R-0118-j): `host_ready{clause}`, `instance_check_total{trigger,status}`, `instance_check_duration_seconds`, `seconds_since_last_ok`; documented alert `host_ready == 0` for 5 min.

| `data_dir_in_use` (startup error) | `{ data_dir, holder }` | Lock held, or the holder record is live or foreign (R-0116-g) |
| `data_dir_postmaster_ambiguous` (startup error) | `{ data_dir, pid, guidance }` | `postmaster.pid` names a live process that is not a postmaster for this directory; not signalled (R-0116-g) |
| `data_dir_not_mounted` (startup error) | `{ data_dir, reason: "not_mounted" \| "bad_value" \| "undeterminable", guidance }` | `MNEMRA_DATA_DIR_REQUIRE_MOUNT` set and the directory is not a mount point, the value is not exactly `1`, or the mount table cannot be read — fails closed (R-0116-i) |

The durability requirement lives in R-0121 and R-0117-d; the data-placement obligation is R-0117-j item 1, binding on the operator's instance.)* the embedded cluster's data directory lives outside the executable and its image at the operator-configured location (`MNEMRA_DATA_DIR`, or the OS per-user app-data default) — never a temporary directory, never the executable's own directory, never a container's writable layer.
