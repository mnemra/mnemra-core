# P-0020: Report Execution Context

**Project:** mnemra-core

## Status

`proposed`

Authored at the reporting engine's [Spec](../glossary.md#spec) stage (Stage 3 of the work-shaping pipeline) and flipped to `accepted` at the spec-exit gate. It resolves the `{{P-ReportExecutionContext}}` open ADR slot in the [Frame](../glossary.md#frame) (the Stage 2 architecture document). The binding requirement text is in the [reporting-engine spec](../../specs/2026-07-03-reporting-engine.md), requirements R-0043 through R-0046, R-0048, R-0050 and R-0060 ([R-codes](../glossary.md#r-codes) defined in that spec).

## Context and Problem Statement

The reporting engine (on the feature register after `1.0.0`, a candidate for `1.3.0` or later) lets operators and agents author declarative reports whose bodies are **caller-authored SQL** executed against the shared mnemra-core substrate. That single fact changes what the read-only-execution guard has to defend against. In the worked reference design (the prior design whose mechanisms this ADR re-derives for Postgres), the guard was an "operator-mistake guard, single operator, local file," with a trust boundary of NONE. Here it becomes an **adversary guard**. Authenticated principals author and invoke reports against one shared Postgres instance, and those principals are multiple humans and agents per workspace, with roles per [P-0009](P-0009-rls-admin-token.md), workspaces per [P-0006](P-0006-v0-tenant-enforcement.md) and a policy envelope per [P-0015](P-0015-provenance-envelope-source-roles.md).

Two mnemra invariants don't extend to this path:

1. **Workspace isolation.** [P-0006](P-0006-v0-tenant-enforcement.md) enforces `workspace_id` by threading a typed `WorkspaceCtx` into a **host-built** `WHERE` clause. A caller-written SELECT has no host-built `WHERE` clause to thread it into, so the P-0006 mechanism can't bind it. And general RLS (Postgres row-level security) **policy** enforcement is deferred at V0 (accepted risk `R-0001`).
2. **Read-only.** Every other read path is host-constructed. Here the statement text comes from the caller.

This ADR locks the **dedicated read-only execution context**. It's the mechanism by which report SQL (both user definitions and built-ins) executes with read-only, workspace-isolation, policy-envelope and cost-containment guarantees that the host can't otherwise provide on caller-authored SQL. The Frame ratified the direction (its decision 2a-3) and locked the property space. For several sub-mechanisms the Frame fixed a candidate space and delegated the pick, and the argument for it, to this ADR. The Frame's decision D3 is the elaborated source; this ADR is the durable, adopter-facing record of the engine's headline security guarantee.

Two ADRs ([P-0006](P-0006-v0-tenant-enforcement.md)/[P-0009](P-0009-rls-admin-token.md)) hold an accepted-risk posture that defers RLS. A scoped exception to that posture needs its own ADR. Reversing the exception, or letting it drift, forces a re-derivation of the engine's headline security guarantee. And external adopters and every downstream security review reference it.

## Decision Drivers

- **P-SecurityLayered (security composes in independent layers): each layer is independently load-bearing.** Read-only must survive the loss of any single mechanism. Workspace and policy isolation must be database-enforced on the one path that application-layer discipline can't reach.
- **The `Security ⇄ Simplicity` conflict edge, resolved default-to-Security.** Caller-authored SQL is an adversarial surface, so the extra mechanism is warranted. The constraint-edge register entry reads "default-to-Security per default-on, never opt-in."
- **The general R-0001 RLS deferral must stand unchanged.** The exception is scoped to exactly the caller-authored-SQL path. Host-constructed queries keep the P-0006 application-layer posture, and the R-0001 trip-wire (the first multi-workspace production deployment) is unchanged. The exception must **converge** with the eventual general RLS activation, not fork from it.
- **`ENABLE ROW LEVEL SECURITY` activates RLS for every role.** Attaching a report-role policy to a table turns RLS on for the host's primary role too. The host stays untouched only if it provably bypasses. That's a correctness precondition of the "deferral-stands" claim, not spec-tier detail.
- **A `READ ONLY` transaction does NOT block `set_config()`.** Postgres doesn't treat GUC changes (changes to its runtime configuration settings) as writes, and `EXECUTE` on `set_config` is a default `PUBLIC` grant. So the session-key integrity property must be proven, never assumed from the transaction mode. This is the review-H1 correction (review finding H1, folded into this record).
- **TrustworthySignal TS2 (a verification signal must mean what it reports; rule TS2): an execution-gating enumeration ships with its reconciliation check.** The grant sets (tables, functions) and RLS coverage are hand-maintained allow-lists that decide what a caller can read and execute. So they carry a check of computed reality against the declared lists, and that check fails on a seeded violation.
- **Cost containment is an availability primitive P-0007 doesn't provide.** [P-0007](P-0007-plugin-resource-limits.md) bounds plugin CPU (fuel/epoch), not Postgres query cost. The report path needs its own timeout, row cap and pool.

## Considered Options

The Frame ratified the **dedicated read-only execution context** direction (2a-3) and locked the property space. So the one genuine option this ADR decides is the **session-key tamper-resistance mechanism**, and the Frame fixed its candidate space at exactly two. (Introducing a third isn't on the table.)

1. **S-a: revoke the GUC-setter surface from the report role.** Remove `set_config(text,text,boolean)` and its `pg_catalog` kin from the report role's function-EXECUTE allow-list. RLS policies stay keyed on the host-set session GUCs (the [P-0009](P-0009-rls-admin-token.md) V0.1 keying shape). No permitted function may set a GUC, directly or indirectly.
2. **S-b: key the report-path RLS on a caller-unreachable value.** Use a per-execution `SET ROLE` to a workspace-bound role, so policies key on `current_user` rather than on a settable GUC.

## Decision Outcome

**The dedicated read-only execution context, with session-key tamper-resistance delivered by S-a (revoke the GUC-setter surface).** Six mechanisms lock.

### D-CTX — All report SQL executes in a dedicated read-only context

All report SQL, user definitions AND built-ins, executes in a dedicated execution context. That context has a dedicated Postgres role, `READ ONLY` transactions and RLS policies scoped to that role. Per-execution session settings carry the **caller's** identity. It also has `statement_timeout`, a host-enforced row cap, and a bounded, separate connection pool. Running built-ins here too is deliberate. [Intake](../glossary.md#intake) Non-goal 1 makes read-only the engine's identity "of any kind," so the execution posture is uniform. Built-ins carry a *third* layer, because their host-built SQL keeps the P-0006 host-threaded workspace predicate. *(Anchors: 2a-3 ratified; P-SecurityLayered; the `Security ⇄ Simplicity` edge resolved default-to-Security. Binding text: spec R-0043-a, R-0060-a.)*

### D-RO — Two independent write-blocks, each alone sufficient

This is the worked reference design's R85 defense-in-depth pair (requirement R85 in that design), re-derived for Postgres:

1. **Report role holds `SELECT`-only privileges**: no `INSERT`/`UPDATE`/`DELETE`, no DDL, no sequence usage.
2. **Every report transaction is `READ ONLY`** (`SET TRANSACTION READ ONLY` / `default_transaction_read_only`).

Either one alone blocks a write, and both apply together. The spec's threat tests prove each independently (spec R-0043-c / threat-test T2). *(Anchors: P-SecurityLayered, each layer independently load-bearing; worked-reference R85. Binding text: spec R-0043.)*

### D-GRANT — Table + function-EXECUTE allow-lists, default-deny exclusions, reconciliation

The report role's readable and callable surface is an **allow-list**. It's the Postgres re-derivation of the worked reference design's SQLite authorizer allow-set.

- **Table grant allow-list: a derivation rule over two canonical sources.** The granted-table set is *derived*, not hand-listed. The substrate's content tables are generated per artifact type from the content-type registry and are manifest-extensible, so a hand-maintained list would drift. Two rules define membership. **(i)** Every per-artifact-type content table created through the host content machinery is in the grant set, and it receives its report-role RLS policies at table creation through that same machinery. This covers **primary tables only**. The machinery's history/shadow tables are excluded, deferred until the first report that needs versioned rows. **(ii)** The product-measurement tables (the dispatch, skill-run and activity measurement families) are enumerated by name in the provisioning DDL, which is the canonical enumeration source the reconciliation parses. Changing the membership *rules* (adding a family, granting a core-entity or substrate table, removing an exclusion) is an amendment to this ADR, not a config knob. A new content type flowing through the content machinery is the rule applying, not an extension.
- **Default-deny exclusions, nameable-complete.** No grant means unreadable. Default-deny excludes these by name: the identity/auth/session tables (`admin_tokens` foremost, then `users`, `sessions` and `workspaces`, since readable workspace rows would disclose tenant existence); the P-0015 policy-audit stores (`policy_write_audit`, `policy_decision_audit`); the retrieval cluster's operator-side instrumentation and audit tables (`egress_events`, whose `payload_audit` carries actual egressed content, plus `retrieval_runs`, `traversal_log` and `index_builds`); the content machinery's history/shadow tables; and the operator-internal substrate tables (`state_config`, `schema_migrations`). These are operator-side signals. Exposing them through caller SQL would itself open an existence-disclosure or content-egress channel. The core-entity tables (`projects`, `agents` and kin) simply aren't granted at V0. They aren't sensitive-class, and adding one is an amendment.
- **Function-EXECUTE surface: the two-part lock.** Postgres grants `EXECUTE` to `PUBLIC` by default, so a table-only allow-list is default-*allow* on the function axis. The callable surface is locked as a two-part structure. **(1) Non-`pg_catalog` functions are default-deny.** They're executable only through an explicit per-function grant enumerated in the provisioning DDL. That list is EMPTY at V0, and adding an entry is an amendment to this ADR. Any in-schema `SECURITY DEFINER` function is categorically outside the permittable set. **(2) `pg_catalog` built-ins are callable except the enumerated revocation classes.** Class (a) is the GUC/session mutators, `set_config` and kin (D-KEY). Class (b) is the server-info/statistics/file-access family: the `pg_stat_*` view and function family, `pg_ls_*`, `pg_read_file`-style file access, and `pg_current_logfile`. A literal positive enumeration of `pg_catalog`'s thousands of built-ins is deliberately not the mechanism, because it would be unauditable and prone to drift across Postgres versions. The auditable invariant is that *no revocation-class function and no non-`pg_catalog` function is executable*, and the reconciliation asserts it. Concretely permitted (the spec's constructible positive cases): `count`, `sum`, `avg`, `min`, `max`, `percentile_cont`, `percentile_disc`, `coalesce`, `date_trunc`, `now`, `pg_sleep` (bounded by `statement_timeout`).
- **PUBLIC-default revocation mechanics.** A plain `REVOKE … FROM <report-role>` doesn't remove a `PUBLIC` grant the role inherits. So for the report path, the revocation SHALL operate on the `PUBLIC` grant itself. One way is `REVOKE EXECUTE ON FUNCTION … FROM PUBLIC` (making function EXECUTE opt-in) with explicit re-grants to the roles that need them. The other is a report role that isn't a member of `PUBLIC`-inheriting groups for the relevant functions. The implementation picks within this shape. The invariant is that no `PUBLIC`-default `EXECUTE` reaches the report role for a revocation-class or non-`pg_catalog` function.
- **Reconciliation check (OC-10 / TS2): the full assertion matrix.** OC-10 is the Frame's operating constraint for this check. The grant sets and RLS coverage ship with a reconciliation check in the same change, and it demonstrably fails on a seeded violation. For each granted table it asserts all of the following: RLS is enabled; the spec R-0050 per-family predicates are present (content-artifact tables carry the workspace-RLS policy AND the P-0015 policy-envelope predicates, and measurement tables carry the workspace-RLS policy); the host primary path provably bypasses via ownership-without-`FORCE`; the report role provably does not (D-RLS); and relkind is constrained to base tables or `security_invoker` views. The relkind constraint is there because a non-`security_invoker` view would evaluate base-table RLS as its owner, silently bypassing the report-role policies. A materialized view can't carry RLS, so it fails the RLS-enabled assertion, fail-closed. On the function axis the check asserts that no revocation-class function is executable, no non-`pg_catalog` function beyond the (empty) inventory is executable, no `SECURITY DEFINER` function is executable, and the executable surface is GUC-setter-free (D-KEY's inside-set assertion).
- **Provisioning and standing trigger: fail-closed, rollback + drift recovery (spec R-0044-e).** The role, grant, revocation and RLS DDL ships migration-borne through the forward-only migration runner, idempotent across fresh init and upgrade-in-place. Content types registered later get their grants and policies at table-generation time through the content machinery. The reconciliation has a standing trigger, not a one-time ship-time gate: it fires on every migration-apply completion and every artifact-table generation. Its failure semantics are **fail-closed at every firing point**. A reconciliation failure aborts the operation that fired it. A failing startup apply means the host refuses to start, and a failing table generation means the table never becomes report-readable. It's never log-and-continue. And there's deliberately no skip-reconciliation switch, because a bypass flag would be the fail-open backdoor. Recovery from a drift lockout is **diagnose-then-reapply**. The structured error names each violated assertion, the idempotent provisioning DDL restores missing state, and surplus state is reversed by hand (`REVOKE` the extra grant, drop the seeded object). That recovery is a runbook entry distinct from intentional teardown. The provisioning change includes a documented, ordered rollback procedure: `DROP POLICY` → `REVOKE` → `DISABLE ROW LEVEL SECURITY` → `DROP ROLE`. `REVOKE` precedes `DISABLE` so the report role stays fail-closed until its access is gone, which avoids a transient cross-tenant window where grants are live and RLS is off. The forward-only migration system doesn't auto-reverse security DDL. An out-of-order teardown can strand RLS enabled without its host-bypass precondition, or open that transient window.

*(Anchors: worked-reference R85.2 (allow-set); P-TrustworthySignal TS2; the discovery-stage security review's default-`PUBLIC` finding. Binding text: spec R-0044, R-0060-b, threat-tests T3/T8/T9/T11.)*

### D-RLS — The scoped RLS exception + the ownership-without-FORCE host-bypass precondition

RLS is **enabled on every table in the grant set, with policies scoped `TO` the report role**. The policies are keyed on session settings the host sets per execution from the caller's validated `WorkspaceCtx`, through a `SET LOCAL` of the workspace id and role. That's the [P-0009](P-0009-rls-admin-token.md) V0.1 keying shape, adopted early on this one path. Per family (spec R-0050), content-artifact tables (policy columns present) carry the workspace-RLS predicate AND the [P-0015](P-0015-provenance-envelope-source-roles.md) policy-envelope predicates. Measurement/metric tables (no policy columns) carry the workspace-RLS predicate only.

**The host-bypass model is a correctness precondition, locked here, and the mechanism is ownership-without-`FORCE` ONLY.** `ALTER TABLE … ENABLE ROW LEVEL SECURITY`, which is required to attach the report-role policy, activates RLS on that table for **every** role, including the roles the retrieval path reads under. The host's primary role stays untouched only if it provably bypasses the newly enabled RLS. So **the primary role owns each granted table and no granted table carries `FORCE ROW LEVEL SECURITY`** (table owners bypass RLS unless it's `FORCE`d). This single mechanism keeps both the host-isolation claim and retrieval's own reads intact. **`BYPASSRLS` on the host/application role is NOT an available alternative** (folded in at review round 2, the "r2 fold"). The spec's R-0062-b carries "the application role holds no `BYPASSRLS`" as a P-0009/P-0010 RLS precondition. A `BYPASSRLS` host role would bypass *every* policy once general RLS activates. That defeats the convergence this decision guarantees, and it forces a `BYPASSRLS` removal at activation instead of P-0009's additive `CREATE POLICY` path. The two mechanisms aren't equivalent, and offering both would hand the implementer a latent misconfiguration. The report role is a non-owner, non-`BYPASSRLS`, non-superuser role, so its policies bind. The OC-10 reconciliation (D-GRANT) asserts this for each granted table: RLS enabled AND the host primary role owns without `FORCE` AND no application role holds `BYPASSRLS` AND the report role provably doesn't bypass.

**Convergence with the general R-0001 deferral.** The general V0 RLS deferral stands. Application-layer `WorkspaceCtx` discipline remains the enforcement on every host-constructed query, and the R-0001 trip-wire is unchanged. The exception is scoped to exactly the path where the deferral's premise (host-built `WHERE` clauses) fails. When R-0001 fires and general RLS activates, the report-path policies **converge** with the general activation. D-KEY's mechanism pick preserves the P-0009 V0.1 session-setting keying verbatim, so the general activation adds host-role policies without reshaping the report-role policies. *(Anchors: 2a-3; P-0006/P-0009 (R-0001); P-0009 V0.1 policy shape; P-SecurityLayered. Binding text: spec R-0045, R-0050.)*

### D-KEY — Session-key tamper-resistance: revoke the GUC-setter surface (S-a)

**The locked property:** the RLS session keys MUST be unreachable from caller-authored SQL. That's proven by threat test, never assumed from transaction mode. A caller's single prepared SELECT, including one with a `set_config()` call in an expression or inside a `MATERIALIZED` CTE, MUST NOT re-key the report-path RLS.

**The mechanism (S-a):** revoke the GUC-setter surface (`set_config(text,text,boolean)` and its `pg_catalog` kin) from the report role through the D-GRANT function-EXECUTE allow-list. The end-to-end argument is that no permitted function can set a GUC, directly or indirectly.

**Why S-a over S-b (the end-to-end argument).** The Frame fixed the candidate space at two. S-b (key on `current_user` via per-execution `SET ROLE`) does **not** escape the GUC channel. In Postgres, `role` is itself a settable GUC. `set_config('role', …)` is reachable from a SELECT expression, and under a role the report role is a member of, a `SET ROLE` is caller-reversible. So S-b's `current_user` key is tamper-resistant only if the GUC-setter surface is *also* revoked. In other words, S-b presupposes S-a and then adds per-workspace role machinery on top (one Postgres role per workspace, or a role-switching layer). S-a delivers the property with the smaller mechanism AND preserves the P-0009 V0.1 session-setting keying verbatim, which is D-RLS's convergence path. S-b would trade keying identity for a role-isolation boundary and owe a separate convergence argument. **The end-to-end argument, channel by channel** (r2 fold: every GUC-writing path a caller could reach, and what closes it). (1) **The function channel.** `set_config` and its GUC-setting kin are revoked under D-GRANT revocation class (a). (2) **The utility-statement channel.** `SET` / `SET LOCAL` / `RESET` are utility statements, and they're structurally absent from the report path. The executor prepares exactly **one** statement (spec R-0047-a) and the write-time gate admits only read statements (spec R-0042-c), so no utility statement is ever prepared. (3) **The catalog-write channel.** `UPDATE pg_settings` never reaches the report path. It's a non-`SELECT` statement, rejected at the write-time gate (spec R-0042-c admits only `SELECT`/`WITH…SELECT` bodies and rejects data-modifying CTEs). Its rule-rewritten form is closed too: `pg_settings` is an updatable view whose rule rewrites the UPDATE into `SELECT set_config(…)`, and the channel-(1) `set_config` EXECUTE revocation closes that. The D-RO write-blocks are NOT the closers here. The rewrite leaves no DML node for the `READ ONLY` block to fire on, and the rewritten call needs `EXECUTE`, not table-write privilege. (4) **The indirect channel.** No *permitted* function can set a GUC on the caller's behalf, because the reconciliation asserts the executable surface is GUC-setter-free. There's no `SECURITY DEFINER` function, no non-`pg_catalog` function beyond the (empty) inventory, and every revocation-class function is non-executable (spec R-0044-d, threat-test T9's inside-set sweep). The write discipline is that the host writes the settings once per execution (`SET LOCAL`, inside the transaction, before the user statement is prepared), and the caller has no channel through which to overwrite them. The threat test seeds a `set_config`/materialized-CTE re-key attempt that demonstrably fails (spec threat-test T1). *(Anchors: Frame D3 fixed two-candidate space; P-SecurityLayered; Simplicity; the folded review-H1 correction. Binding text: spec R-0046.)*

### D-COST — Query-cost containment

- **`SET LOCAL statement_timeout`** per execution (default 10 s, spec-pinned; config-tunable). It's an availability primitive that [P-0007](P-0007-plugin-resource-limits.md)'s plugin CPU limits don't provide.
- **A host-enforced row cap** (default 10,000, spec-pinned) with **reported truncation**. The result envelope carries a truncation flag and the capped count. It's never a silent trim (P-TrustworthySignal).
- **A bounded, separate connection pool** (default max 4, spec-pinned) so runaway report load can't starve the host's primary pool. The pool is process-global at V0. The spec's calibrations name the noisy-neighbor trade-off plainly, and per-workspace scoping is deferred. **Saturation is caller-visible, never a hang** (r2 fold). Acquisition uses a bounded acquire-timeout (default 2 s, spec-pinned). When it expires the caller gets a structured pool-saturated error, which is retry-safe. P-0007 takes the same fail-fast posture against indistinguishable hangs on the plugin path, and it's taken here too. On host shutdown, in-flight report queries are cancelled. That's safe by construction, since the transactions are read-only.
- **The host-enforced calibrations are config-backed and startup-validated** (spec R-0048-e). Unset means the spec default. An invalid value fails startup and names the key. Hardcoded constants would silently void the config-tunable property the calibrations promise.
- **A cost-*estimate* ceiling (planner-cost rejection before execution) is deferred.** The decision content is whether to add an `EXPLAIN`-based pre-execution cost gate, and its threshold. The deferral anchor is [P-Defer](../glossary.md#p-defer) (defer mechanism choice until evidence forces it): timeout plus cap bound the damage, and a cost model would be mechanism ahead of evidence. The deferral uses the `P-LockContract ⇄ P-PreserveDecisionSpace` discriminator (see [P-LockContract](../glossary.md#p-lockcontract) and [P-PreserveDecisionSpace](../glossary.md#p-preservedecisionspace)). The firing instrument is the spec's telemetry reporting timeout-kill events at or above the spec-pinned rate, computed over the retained emitted stream (spec R-0059-b).

*(Anchors: P-0007 (the gap); P-TrustworthySignal; P-Defer. Binding text: spec R-0048.)*

### Consequences

**Good:**
- Read-only holds adversarially. There are two independent write-blocks, each alone sufficient, plus single-statement-by-construction and bind-never-interpolate.
- Workspace isolation is database-enforced on the one path the P-0006 application layer can't reach. The general R-0001 posture is unchanged elsewhere, and there's a clean convergence path.
- The session-key integrity property is proven, not assumed. The folded review-H1 factual error (the claim that `READ ONLY` blocks `set_config`) is corrected by the revoke-the-setter mechanism.
- The grant sets and RLS coverage carry a reconciliation check that fails loud on drift (TS2). The silent-gap class (a granted table without a policy) fails the check, not the tenant.
- Cost containment closes the availability gap that P-0007 structurally can't.

**Bad / Trade-offs:**
- The report path activates RLS early on one role, ahead of the general activation. That's added mechanism compared with a pure application-layer posture, and the adversarial surface warrants it (the `Security ⇄ Simplicity` edge, resolved default-to-Security).
- The ownership-without-`FORCE` host-bypass model is a correctness precondition the reconciliation must assert for each granted table. A misconfiguration here silently weakens host-path isolation. That's why it's locked scope (with `BYPASSRLS` explicitly excluded) and reconciliation-checked rather than left to review.
- Some grant-surface enumerations remain hand-maintained: the measurement-table list in the provisioning DDL, the exclusion list, and the function revocation classes. Those are drift surfaces. The mitigation is the reconciliation check *with its standing migration-apply trigger*. The content-table side is derived by rule rather than listed, and extension-by-amendment (not config) keeps the rules auditable.
- System-catalog readability. `pg_catalog` metadata (schema shape, not row data) is readable by default, so disclosure is bounded to the structure of a shared-schema instance. The spec carries the hardening-checklist artifact ([spec §pg_catalog hardening checklist](../../specs/2026-07-03-reporting-engine.md)), authored at the r2 fold. It records the `pg_stats`/`pg_statistic`/`pg_stats_ext` sampled-value surfaces as closed via the built-in RLS guard, contingent on R-0045 enablement and pinned to the embedded Postgres 16.4. It also enumerates what can and can't be revoked without breaking query planning. The risk is accepted as Low, with this ADR owning the disposition.

## Pros and Cons of the Options

### S-a — Revoke the GUC-setter surface (chosen)

- Pro: it delivers the locked property with the smallest mechanism, and the function-EXECUTE allow-list already gives it structural footing.
- Pro: it preserves the P-0009 V0.1 session-setting keying verbatim, which is the D-RLS convergence path.
- Con: it relies on the GUC-setter revocation being complete (every direct and indirect GUC-setting function). The end-to-end argument and the T9 function-allow-list threat test are the mitigation.

### S-b — Key RLS on `current_user` via per-execution `SET ROLE`

- Con: it doesn't escape the GUC channel. `role` is a settable GUC, and `SET ROLE` is caller-reversible under shared role membership, so S-b presupposes S-a's revocation anyway.
- Con: it adds per-workspace role machinery (a role per workspace or a role-switching layer) on top of the revocation S-a already needs.
- Con: it trades keying identity for a role-isolation boundary and owes a separate convergence argument against the general R-0001 activation.

## Amendment 2026-10-25 — The `pg_stats` closure rests on a capability, not an engine version

Applied 2026-10-25 under the maintainer's rulings on #4249: activity 8285 (design records carry no runtime-engine version) and 8303 (confirming 8296: an exact pin of a runtime system stays out; a minimum version of an operator-run system is interface and stays). The stated reason is that a version change must never require reopening a locked record.

**Superseded (the text above is kept as the record):** "pinned to the embedded Postgres 16.4" in the System-catalog readability trade-off. Following the amended [reporting-engine spec](../../specs/2026-07-03-reporting-engine.md) §pg_catalog hardening checklist, item 1, the sampled-value closure rests on the built-in row-security guard on the `pg_stats` / `pg_stats_ext` views. That guard is present in PostgreSQL 9.5 and later. Its re-verification is **parked, human-noticed** (`P-Defer` DF1, the rule that a deferral with no mechanical trigger is parked and re-checked by a person on a stated cadence). No check detects a change to the PostgreSQL releases the host admits, so the spec's auditable `pg_stats` check is re-run by hand at the cadence that spec item names. That cadence is plan pickup and the reporting engine's `designed` → `committed` transition (two [feature register lifecycle tiers](../glossary.md#feature-register-lifecycle-tiers)). The embedded engine itself was superseded by the operator-run instance ([P-0010](P-0010-storage-substrate-engine.md) §Amendment 2026-10-19). The accepted-Low disposition and this ADR's ownership of it are unchanged.
